# Feature: v0.5 milestone — `Transport` trait + `LocalOnly` (sync staging Milestone 0)

## Summary
`docs/SPEC.md` §10 sketches a `Transport` trait (`LocalOnly` → `HostedRelay` →
`AtProto`) that has never been formalized in code — `store::log::Log` talks to
local disk directly, with no seam for a second transport to plug into. This is
Milestone 0 of `.design/sync-layer-architecture-and-staging.md`'s staging plan
(ADR-35's roadmap: "Specified, ready to build" for v0.5.0-beta.1): define
`src/transport.rs`'s `trait Transport` and its first, honest implementation,
`LocalOnly`, wrapping `store::log::Log` — with zero change to `Workspace`, the
CLI, or MCP. Four signature/shape decisions the sync-layer doc deliberately
left to this pass (its REQ-1 explicitly says "adapted... not a literal
transcription of the spec's illustrative signatures") are resolved below by
checking real code (`Log::append`, `Log::iter_all`, `Log::current_root`) rather
than guessing from `docs/SPEC.md` §10's pseudocode.

## Requirements

- REQ-1: `src/transport.rs` (new top-level module, declared in `src/lib.rs`
  alongside `relations`/`workspace`/`context` — `Transport` is about *where*
  claims come from/go to, a different axis than `store/`'s *how they're
  persisted once here*, matching the sync-layer doc's original framing)
  defines `trait Transport` with two `async fn`s, matching `store::log::Log`'s
  actual established shape rather than `docs/SPEC.md` §10's illustrative
  pseudocode:
  ```rust
  pub trait Transport {
      async fn publish(
          &mut self,
          content: crate::claim::ClaimContent,
          identity: &crate::sign::Identity,
      ) -> Result<atproto_dasl::Cid, Error>;

      async fn subscribe(
          &self,
          dids: &[crate::claim::Did],
      ) -> Result<ClaimStream, Error>;
  }
  ```
  `publish` takes one unsigned `ClaimContent` + `identity` and returns the new
  claim's `Cid` — the exact shape of `Log::append` (`src/store/log.rs:852`),
  not `docs/SPEC.md`'s illustrative `fn publish(&self, &[Claim])` batch — since
  `Log::append` is the only thing `LocalOnly` wraps and it signs one claim at a
  time; inventing batching or pre-signed-`Claim` input here would give
  `LocalOnly` a shape it can't honestly implement without new `Log` surface
  REQ-3 doesn't ask for. `&mut self` matches `Log::append`'s own `&mut self`
  receiver (the MST/commit chain mutates on every append).
- REQ-2: `subscribe` returns a real stream, not a `Vec` — `ClaimStream =
  std::pin::Pin<Box<dyn tokio_stream::Stream<Item = Result<crate::claim::Claim,
  Error>> + Send>>`, using `tokio-stream` (thin wrapper around the same
  `futures-core::Stream` trait; already sits in the tokio family kan depends
  on for its async runtime, `Cargo.toml`'s existing `tokio = { features =
  ["rt", "rt-multi-thread", "macros", "fs", "io-util"] }`) — a new,
  minimal dependency (no macros, no combinator surface beyond what
  `tokio_stream::empty()` needs). `Item = Result<Claim, Error>`, not bare
  `Claim`, so a future networked transport (`HostedRelay`) can surface
  mid-stream errors (a dropped connection, a bad record from a peer) without
  a signature change later — `LocalOnly`'s stream just never yields an `Err`,
  since it never yields anything at all. Carries the signed `Claim`
  (content + sig — what actually crosses a trust boundary and what
  `docs/SPEC.md` §10's sketch names), not `store::log::StoredClaim` — the
  `rev` TID (`src/store/log.rs:147`) is log-internal ordering, meaningless
  once claims are read back through a boundary that isn't "this one MST."
- REQ-3: `LocalOnly` (in `src/transport.rs`) implements `Transport` by
  wrapping `store::log::Log`: `publish` delegates directly to
  `Log::append(content, identity)`, returning its `Cid` unchanged. `subscribe`
  is **not a stub** — for `LocalOnly` specifically there is no other actor's
  log to subscribe to (one author, one log, per `docs/SPEC.md` §10's "`LocalOnly`
  (no-op)"), so it correctly returns `Ok(tokio_stream::empty().boxed())` — the
  honest answer for this transport, not a placeholder waiting to be filled in.
- REQ-4: A new `transport::Error` enum (not a reuse of `store::log::Error`
  directly) with `#[error("log error: {0}")] Log(#[from] store::log::Error)` —
  keeps `Transport`'s error surface decoupled from `LocalOnly`'s specific
  backing store, so `HostedRelay`'s own error variants (network, auth) have
  somewhere to live later without `store::log::Error` growing transport-shaped
  variants it has no business having.
- REQ-5: Zero change to `Workspace`'s public shape, `actions.rs`, the CLI, or
  MCP surface. `Transport`/`LocalOnly` are additive — not yet threaded through
  `Workspace` (which still holds a concrete `log: Log` field directly, as
  every existing test file that constructs `Workspace { .. }` by hand already
  assumes, e.g. `tests/workspace_staleness.rs`). Wiring `Transport` into
  `Workspace` is deliberately deferred to Milestone 2 (`HostedRelay`,
  v0.6.0-beta.1's identity work lands first per ADR-35's sequencing, then
  `HostedRelay` at v0.7.0-beta.1), where a second real implementation exists
  to design the wiring against.
- REQ-6: `LocalOnly`'s behavior is proven equivalent to today's direct
  `Log::append` usage — same `Cid` for the same content — via a dedicated
  test, not asserted by inspection alone. Proof method: `crate::cid::content_cid`
  (`src/cid.rs:19`) is a pure function of `ClaimContent` alone, so appending
  identical content once directly through `Log::append` (in one temp log) and
  once through `LocalOnly::publish` (in a second, independent temp log)
  must yield identical `Cid`s — this proves `publish` doesn't alter, wrap, or
  reorder the content before handing it to `Log::append`, without needing new
  read-back accessors on `LocalOnly` beyond what `Transport` itself defines.

## Architecture
`src/transport.rs` sits at the same level as `relations.rs`/`context.rs`/
`workspace.rs` in `src/lib.rs`'s module list (REQ-1). `Log::append`
(`src/store/log.rs:852`) and `Log::iter_all` (`:1245`) already have exactly the
`async fn ... -> Result<_, Error>` shape `Transport`'s methods adapt — this is
adaptation of an existing pattern, not a new one, matching the sync-layer
doc's own framing.

`LocalOnly` is a one-field wrapper:
```rust
pub struct LocalOnly {
    log: crate::store::log::Log,
}

impl LocalOnly {
    pub fn new(log: crate::store::log::Log) -> Self {
        Self { log }
    }
}

impl Transport for LocalOnly {
    async fn publish(&mut self, content: ClaimContent, identity: &Identity)
        -> Result<Cid, Error>
    {
        Ok(self.log.append(content, identity).await?)
    }

    async fn subscribe(&self, _dids: &[Did]) -> Result<ClaimStream, Error> {
        Ok(Box::pin(tokio_stream::empty()))
    }
}
```
`tokio-stream`'s `?` conversion from `store::log::Error` is REQ-4's `#[from]`
doing the work — no manual `.map_err` at the call site, matching every other
`Error` enum in the codebase (`workspace::Error`, `actions::Error`).

**The trait signature is not trying to be final** (the sync-layer doc's own
words about M0, worth restating here since this doc pins down more of the
shape than that one did): the real shape `HostedRelay` needs — auth tokens,
retry/backoff, partial-failure handling across a network boundary, whether
`publish` needs to become fallible-and-retryable in a way `Log::append`'s
single local write never is — isn't knowable yet from `LocalOnly` alone.
`HostedRelay`'s own `/design` pass (Milestone 2 in ADR-35's roadmap, gated on
issue #7's E2EE design and issue #30's identity work landing first per that
doc's sequencing) may need to widen or change this trait. M0's job is proving
the pattern — a real seam exists, `LocalOnly` is its first honest
implementation, nothing downstream breaks — not nailing a signature that
survives every future transport unchanged.

**No touchpoint with the fold, the append-only log's actual persisted
content, or anchors.** `LocalOnly::publish` is a pure delegation to the
already-battle-tested `Log::append` (ADR-12/13's incremental-append work) —
this milestone adds a seam in front of it, not new persistence logic. kan's
non-negotiable invariant (no operation destroys a subject) isn't at risk here
because nothing in this milestone writes, mutates, or reads the claim graph
differently than it already does today.

## Open Questions
None — every question this pass raised (publish's exact signature vs. SPEC's
batch-of-signed-Claims sketch; subscribe's return type — `Vec` vs. a real
`Stream`, and the resulting new-dependency choice; whether the stream item is
`Claim` or `StoredClaim`; where `Transport::Error` lives relative to
`store::log::Error`) was resolved in conversation before this doc was written.

## Out of Scope
- **Wiring `Transport` into `Workspace`/`actions.rs`/the CLI/MCP** — deferred
  to Milestone 3 (`HostedRelay`, ADR-35's roadmap), once a second real
  implementation exists to design the wiring against (REQ-5).
- **`HostedRelay`'s and `AtProto`'s actual protocol/wire-format design** —
  staged as Milestones 3 and 4 in `.design/sync-layer-architecture-and-staging.md`,
  their own future `/design` passes.
- **Issue #7's E2EE design** and **issue #30's per-agent identity design** —
  independent tracks per ADR-35's sequencing, not part of this milestone.
- **Any real second-actor subscribe behavior** — `LocalOnly::subscribe`'s
  empty-stream answer is correct *because* there is no second actor yet in
  the local-only spine; a real multi-log subscribe implementation only makes
  sense once `HostedRelay` exists.
- **The version bump / release PR** (`Cargo.toml` → `0.5.0-beta.1`, tag push)
  — per every prior milestone's precedent (v0.2/v0.3/v0.4), this is its own
  follow-up PR after this milestone's build PR merges, not part of this doc.

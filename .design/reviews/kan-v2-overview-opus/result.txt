## Overview findings
- **O1 (medium, must fix in code):** the active-journal read holds its database lock while it parses and hashes every row. Health-journal writes give up after waiting 100 ms.
  - Debug build, 60k-row journal: the lock was held about 1.3 s, and every concurrent health write failed with "database is locked".
  - Release build, near the 32 MiB limit: scans took 108–259 ms, writes stalled up to 158 ms, and 4 of 10 refreshes failed. No writes were lost on this machine, but slower hardware would lose them.
  - This contradicts the design's requirement to release the transaction promptly and prove capture continues, and the runbook's "health writers continue". The author's test only writes after the lock is released, so it can't catch this.
  - Fix: copy raw values inside the transaction, end it, then parse and hash, and add a regression test. Rewording the docs won't close this.
- **O2:** "database busy" and "rotation in progress" errors both show as "source invalid or unavailable".
- **O3:** Build and Cancel clicks are silently ignored while any overview request, including the 5 s poll, is in flight (`web/operations/app.js:119`).
- **O4:** memory accounting is safe but about 4× too cautious (26 MB actual vs 109 MB counted). The budget runs out at about 85k distinct attempts, so the documented 250,000 limit can never be reached.
- **O5:** a cached sample looks exactly like a fresh one (only the build time differs), and the "superseded" state named in AC-5 doesn't exist.

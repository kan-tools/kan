  binding all refuse (PO4: 12 hostile active-row cases; PO4b: 3 invalid unique-attempt cases).

  attempts and sessions (PO10 overflow; OM13 killed only by PO10).

  mode, mtime and SHA-256 unchanged; no -journal/-shm/.lock created (PO2). A missing generation

FINDINGS (Scope A)
O1 [MEDIUM - design-required qualification not met; REQUIRED code fix]
   The active snapshot holds its rollback-journal read transaction while parsing every body,
   serialising each row twice (digest + cost) and hashing: src/evidence_operations/projection.rs
   scan_projection, `let tx = self.conn.unchecked_transaction()?` (line 42) through
   `tx.commit()?` (line 132), with per-row serde/hash in between. Journals use
   journal_mode=DELETE (evidence_operations.rs:138) and writers have busy_timeout 100 ms
   (evidence_operations.rs:242); the health writer counts any record error as a loss
   (evidence_operations.rs:799-801).
   Evidence: debug, 60,021-row/25.4 MB active generation: read held 1.28-1.30 s; 8/8 and 9/9
   concurrent health writes failed "database is locked" (PO1, raw/08). Release, 72,021 rows/
   30.6 MB (within the 32 MiB profile): active scans 108-259 ms; writer stalls up to 158 ms vs
   17 ms control; 4/10 refreshes themselves failed "database is locked" (PO1b, raw/09b). No writer
   loss was observed in release on this Apple-silicon host, but the margin against 100 ms is
   hardware-dependent and already exceeded by the observed stalls.
   This contradicts the design ("Copy only typed row values into bounded memory, then end the
   SQLite transaction promptly"; "Qualification must prove that active capture still proceeds")
   and docs/V2-OPERATIONS.md ("promptly releases their SQLite transaction ... Active health
   writers continue"). The author's pinned_active_snapshot_... test writes only AFTER
   Boundary::ActiveRead, i.e. after commit, so it cannot fail on this.
   Not a BLOCK: evidence capture (encrypted queue) is unaffected, health losses are counted in the
   lower-bound telemetry, and refresh is explicit and owner-triggered. Fix in code: copy raw
   column values (budget-accounted) inside the transaction, commit, then parse/validate/digest
   outside it. Add a regression that writes during the scan of a near-ceiling journal and
   asserts zero writer errors and a bounded hold. Narrowing the doc claim does not close O1.
O2 [LOW-MEDIUM] Contention, rotation-in-progress and other I/O errors all surface as
   "source invalid or unavailable" (Manager error mapping in overview.rs). Under a continuously
   writing health thread about 40% of refreshes fail with wording that suggests source damage.
   Distinguish busy/in-use from invalid.
O3 [LOW-MEDIUM, UI] Build and Cancel clicks are silently ignored while any overview request,
   including the 5-second background poll, is in flight. Cause: web/operations/app.js:119 loadOverview
   `if(!token||overviewBusy)return;`. Shown by UP2 and UP3, which fail on baseline. A dropped
   Cancel leaves the operator believing cancellation was requested. The window grows over an
   authenticated tunnel.
O4 [LOW-MEDIUM, claims] Accounting is about 4x conservative, at roughly 1.3 KB accounted per
   distinct attempt (PM1). The default 128 MiB budget therefore runs out at about 85k distinct
   attempts. The documented "250,000 distinct attempts" ceiling can never be reached: one full
   32 MiB generation (~75k rows) fits, but two full generations of distinct attempts do not.
   Either state the effective bound or calibrate the accounting with a heap-measurement
   regression like PM1. The current behaviour is safe: it fails closed as capacity-limited.
O5 [LOW-MEDIUM, AC-3/AC-5 labeling] A sample fetched by "Load last sample" renders exactly like
   a fresh build ("Overview completed"); its age shows only through the absolute build time.
   - The UI does not compare the sample's active generation with the current one, although
     /api/status already reports it in journal.scope.
   - AC-5's "superseded" state does not exist in Published.state.
   - An invalid response after a valid sample keeps the prior totals on screen beside "Invalid
     overview snapshot.", without the "Prior sample retained" label (UP5).
O6 [LOW, regression gaps] The author suite does not kill:
   - OM2 (missing lock-file check; without it the projection would create a .lock file)
   - OM3 (scan valid_health; invalid unique rows would be summed)
   - OM11 (Transfer-Encoding refusal)
   - OM13 (checked session sum)
   - UM2 (generation guard on the error path)
   OM1 (post-read sealed rehash), OM5 (sealed worker suppression) and OM6 (sealed sidecar
   refusal) also survive my probes. The post-read rehash has no deterministic test seam.
   Incorporate PO2, PO3, PO4b, PO5 (failure classes), PO9, PO10 and UP1.
O7 [LOW, evidence wording] The design's "Rust and real-browser qualification are complete for
   this checkpoint" overstates the coverage:
   - The real browser covered only completed + lock. Building, capacity-limited, failed and
     cancelled were exercised only through Node with synthetic responses.
   - Overview connection limits are untested.
   - The design's own active-capture qualification was not performed (O1).

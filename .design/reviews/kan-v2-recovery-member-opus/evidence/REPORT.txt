Findings A
- A-F1 [MEDIUM — design incoherence, implementation follows one side. Resolve before any creation writer signs
  `unavailable`.]
  - The codec has two rules that contradict each other:
    - codec :165-166: "wrong length/hash produces corrupt entries".
    - codec :406-408, the governing checkpoint: "A hash-valid request that fails its writer signature or exact
      manifest binding is invalid member evidence, not a repairable missing-byte condition".
  - The code folds the length check into byte validity (:447-449). It never reaches writer/manifest
    verification for a hash-valid object whose issuer-signed length is false.
  - RP14a shows genuine original request bytes reported as Corrupt, with the member accepted. The fault is
    attributed to the raw bytes, not to the false signed metadata.
  - Consequences:
    - A future observer would sign an `unavailable: corrupt` statement about authentic bytes.
    - The coordinate can never be restored, since any CID-matching candidate has the "wrong" length.
  - No false completion or publication is possible: there is no consumer, and publication re-verifies.
  - Same class, also accepted as a loss:
    - RP14b, an empty-CID with a positive signed length.
    - Signed lengths above evidence_service MAX_REQUEST (2 MiB + 4 KiB, src/evidence_service.rs:14-15), which no
      valid service request can have.
  - Required: decide which rule governs. For hash-valid bytes with a disagreeing authenticated length, refusing
    as invalid member evidence matches the checkpoint text and the north star (do not misattribute raw data).
    Then pin it in both implementations.
- A-F2 [LOW-MEDIUM — authentication gap in a reported projection]
  - Partial profile-3 membership is unauthenticated: the plan digest needs every source commit (RP02;
    copied.rs:200-203 has the same property).
  - Member.losses() nevertheless emits null coordinates and expected lengths derived from it.
  - The only signal is recipe_metadata_complete()==false. The loss entries themselves do not say which
    coordinates are authenticated.
  - Codec :103-105 says expectedLength comes "from authenticated metadata/membership".
  - Partial members cannot publish in KNB1, but a creation writer would still sign these coordinates.
  - Required before creation:
    - EITHER mark membership-only coordinates in partial members as unauthenticated, or withhold them,
    - OR state in the design that partial-copy membership is attested only by the external copy job.
- A-F3 [LOW — early-detectable impossibility deferred]: shared request CIDs across distinct (writer, op)
  occurrences (RP03) are accepted when the bytes are missing.
  - Static service requests make this unsatisfiable: the request bytes fix one operation and position.
  - Codec :157-158 deliberately keeps per-occurrence coordinates, and the Member claims no recoverability, so
    this is consistent but weak.
  - Consider refusing it outright for the service-request payload profile.
- A-F4 [LOW — test pinning]
  - The author suite does not pin these guards:

    - historical receipt issuer
    - source tip
    - plan scope/issuer binding

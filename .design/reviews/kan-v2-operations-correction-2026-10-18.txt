## Findings (none blocking)

1. **The production startup path has almost no direct tests.** All five regression tests use `ops::reporter(Journal)`; the CLI uses `reporter_at` (`src/bin/kan-v2.rs:869`). Only the CLI test touches it, and only with a missing journal. The documented rule that "a mismatched journal is never written" (`docs/V2-OPERATIONS.md`) holds when I run it (P2), but nothing in the suite would catch it breaking (C1).
2. **A truly full journal silently stops counting losses.** In probe P1 I filled the journal and then restarted the reporter 300 times, sending 20 updates per start:
   - Only the first 88 session rows fit. After that, `telemetry_dropped` stayed at 1,760 even though 6,000 updates were lost.
   - The docs say losses "increment… when persistence returns". Without an erase or rotate command, persistence never returns.
   - The dashboard shows only the generic "gaps are retained" warning. Nothing reports that the journal is full or that capture isn't being recorded.
   - Startup still works. This is a visible gap with the wrong size.
3. **Worker history is reset when the journal comes back late** (probe P6). `last_ack_at` and `last_ack_position` change from recorded values to `null`, and `telemetry_failures` drops from 7 to 3 (`src/evidence_operations.rs:378-388`). The docs call this counter "accumulating", but here it goes down.
4. **The dashboard can no longer show "Status is current"** (`web/operations/app.js:32-34`). A healthy, active reporter always gets the "N reporting session(s) are active or ended without a clean close" warning. That's conservative, but it trains operators to ignore warnings, which the first review also raised.
5. **Known limits that are disclosed:** the 256-item queue can drop the newest snapshot during bursts (coalescing is a named follow-up), and the byte and record caps are independent. Both are documented accurately.

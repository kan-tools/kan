## Does the P4 fix close the flake?
- **It passes reliably.** P4 passed 30/30 alone, 10/10 in full-suite runs and once more after a clean rebuild. Observed equalled queued in every run (87 or 88 events, 0 unconfirmed).
- **The failure cause is removed.** In 7 runs, none of the periodic lock attempts succeeded, so the coordinated window was the only one. The parent counted from zero, so each of those would have failed `held > 0`. The first window lasted 5.1–7.6 ms and always fell inside the capture interval.
- **Active window versus actual SQLite wait.** P4 only checks that the writer's self-reported window sits inside capture's run time. To see whether capture really waited, I ran a temporary instrumented copy that records what production returns. In 35 of 35 runs, the first admission started about 5 µs into the window. Production's busy handler then reported 8.1–9.1 ms of real waiting, and the admission succeeded. So capture really does wait, but only my probe shows it; P4 doesn't assert it. Later periodic windows remain sparse (0–4 per run).
- **It exposes capture defects instead of hiding them.** I broke production so capture never waits, and separately capped its wait at 1 ms. The new P4 failed 10/10 on each, both times on the named check `brief contention must not disable capture`. The parent's P4 also failed every mutated run, but 3 of 20 were on its own `held > 0`, so the capture assertion wasn't what fired. The separate Q2 test also catches both.
- **Can the coordination be removed silently?** Mostly no:
  - Not installing the window, or skipping it in either Sink method, fails with `capture must reach its first admission`.
  - Reordering the writer's acknowledgement, or not waiting for it, makes the writer's own lock fail with `DatabaseBusy`.
  - **One gap:** keeping the handshake but deleting the lock inside the first window still passes. `held` now starts at 1, so `assert!(held > 0)` can never fail. My probe showed the fix: asserting that the first admission waited (`spent > 0`) passed 10/10 normally and failed 5/5 with the lock deleted.
  - Throwing away the returned wait value also passes, so the claim that it is preserved isn't checked. It's harmless here.
- **Cleanup works.** If capture panics before its first admission, the test fails in 46 ms and reports capture's panic. If it panics after forwarding, the writer is stopped and joined and the test fails in 1.35 s. Nothing hung or leaked.

SCOPE A - OVERVIEW CORRECTION (262cad3)

Mechanism, read from code (src/evidence_operations/projection.rs:41-79,
src/evidence_operations_collection/overview.rs:233-292, 401-411):
- Journal::open_file validates the live source.
- projection_copy sets the source busy_timeout to 0 and creates a :memory: destination
  (page_size 4096, max_page_count 8192).
- It runs sqlite3_backup in 64-page steps, checking cancellation before every step. Busy or Locked
  steps sleep 1 ms. A 5 s deadline returns SourceBusy.
- It then revalidates schema/control rows on the copy and swaps the copy in. The live connection is
  dropped before any row is parsed.
- snapshot.started_at/finished_at are overwritten with the copy window.
- Sealed generations are still read in place under a pre-hash and an exact post-read rehash.

Independent verification (probes/zz_review_overview_correction.rs; writers run as SEPARATE PROCESSES):

  continuous (~55-60 commits/s, fsync bound), 20 Hz and 5 Hz.

- Max write latency 19-24 ms, about the fsync baseline. No write exceeded 50 ms.

SCOPE C - PROFILE-3 COPY-UPGRADE DESIGN (design readiness only; no runtime exists or was judged)

Sound:
- A separate profile 3 instead of silently widening profile 2.
- The plan binds:
  - recipe 1 and source profile 1
  - exact through/tip
  - a framed digest over ordered manifest, receipt and retained-request CIDs. Alternate valid
    snapshots at the same through/tip are distinguished.
  - single H
  - target scope and C
  - target profile 3
  - a 32-byte nonce
- archiveId = domain-separated SHA-256(plan bytes). Proofs bind archiveId, so every C-signed proof
  transitively commits to the plan. No mutable progress flag is needed.
- Completion is derived: verified prefix length + digest + H before any admission.
- An incomplete prefix refuses Append.
- The proof chain is exactly the retained-verified prefix followed only by admitted rows.
- An empty source needs explicit H.
- Exact resume never replaces or re-signs.
- Backup/recovery must carry the plan and refuse a changed plan.
- The qualification list is strong:
  - independent plan vectors
  - field mutations
  - alternate snapshots
  - partial-copy admission
  - concurrent destination changes
  - every interruption point
  - source/WAL invariance

Gaps to resolve in the design BEFORE implementation:
C1 [REQUIRED, resume ambiguity] Plan custody before durability is unspecified.
   - Planning happens "before creating any destination". The plan is durable only inside the
     destination.
   - An interrupted creation (an empty file, exactly as in profile-2 init) therefore has no stored
     plan. The owner has only the pinned ID.
   - "Exact resume" then requires either an owner-held plan artifact or atomic schema+identity+plan
     creation plus a resume input that re-supplies the same plan bytes.
   - Re-planning mints a new nonce and a new archiveId.
   - Specify the artifact, its integrity check (it must hash to the pinned ID) and the empty-file
     resume rule.
C2 [FOLLOW-UP, equivocation] Re-executing one plan into a second fresh destination, or resuming a
   backup of an incomplete copy alongside the original, yields two archives with the SAME
   commitment-derived ID and diverging admitted suffixes.
   - This is the known restored-writer fork class (design lines 257-262).
   - The design should name it for profile 3, distinguish create-from-plan from resume, and say that
     only one destination per plan may ever admit.
C3 [REQUIRED, backup/recovery coherence] Earlier text says a payload-incomplete recovery copy
   "remains profile 2" with an authoritative recovery descriptor and append-only resolution records
   (lines 313-319, 383-389).
   - The new section says profile 2 has an exact schema with no extra fields.
   - Decide whether profile 3 also carries descriptor/resolution tables (and how a profile-2 archive
     records them), before the profile-3 schema and surface catalog are frozen. Otherwise profile 4
     follows immediately.
C4 [REQUIRED, trust binding stated] State explicitly that:
   - archive_identity (archive, scope, issuer) must equal (SHA-256 commitment of the plan,
     plan.scope, plan.C)
   - the stored plan's target profile and recipe must match the opener
   - every opener (writable, verify, backup, rebuild, inventory) recomputes this
   It is implied today, not stated.
C5 [FOLLOW-UP, precision]
   - Define the digest framing with an explicit sequence and count.
   - Say whether the "plan envelope" is signed. Unsigned appears sufficient because of the ID
     commitment; the word "envelope" is ambiguous.
   - Say that per-batch recomputation is digest-only, with signatures verified once per copied row.
     Re-verifying every request per batch is O(n^2/batch).
C6 [FOLLOW-UP, scope] State that legacy histories containing non-service or raw-imported commits
   (no single retained signed request per manifest) cannot be upgraded by recipe 1.

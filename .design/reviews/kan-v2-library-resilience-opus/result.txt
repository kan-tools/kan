## Findings
- **F1 – Privacy, low:**
  - Nothing about failed scopes appears in the JSON, but response time does reveal how many groups of four had a stalled check.
  - P3 measured 5.10s with stalled scope 0, 5.10s with 0 and 1, and 10.02s with 0 and 4.
  - That gives a lower bound on stalled sources. It doesn't identify them, and fast failures (forged, refused) don't show.
  - The docs' "without identifying or counting them" is only true of the response body.
- **F2 – Test gap, medium:** R03, R08 and R12 are correct in code but not pinned by committed tests. My P1 and P2 assertions kill each one.
- **F3 – Test gap, low-medium:** R24 and R31 survive, and so do the ±1s deadline mutants R11 (6s upstream) and R13 (4s body). `serve()` does call the tested helper (R30 killed), but the live socket limit isn't exercised.
- **F4 – Evidence:** I did not rerun the browser. Download delivery is unverified.
- **F5 – Cosmetic:** after a failed retry, the coverage banner keeps its old `partial` styling (`app.js:40`). The client also doesn't validate the shape of scope entries; the server rechecks pins, so this grants no extra access.

## Scope narrowing and house rules
- All four instances of narrowing language are legitimate: download delivery is still marked unverified, the per-scope error rows were dropped on purpose for privacy, a slow source is shown as partial rather than absent, and the out-of-scope roadmap items stay required.
- No house-rule violations: no store mutation, no stored computed values, no enforcement hooks, no new write authority. The v2 frontend is authorized by the owner.

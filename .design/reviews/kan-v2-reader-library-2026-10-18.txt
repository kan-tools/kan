## Findings
1. **Missing and corrupt objects look the same, and one bad object breaks a whole page** (AC-3 unmet; probe 06).
   - I deleted or corrupted one object after the service started. Snapshot still works, but every page containing that record fails as `Corrupt`, and so does `source`.
   - `Missing` only means "beyond the pin" (`src/evidence_reader.rs:248-250`). The cause is service-side: a missing object is mapped to `Corrupt` (`src/evidence_service.rs:672-674`), and Page verifies every row's object (`:625-627`).
   - The server returns 503 and the UI locks the whole session on any error (`web/library/app.js:26,30`). Since the UI always starts at page 0, one bad object in the first 20 entries makes that scope unbrowsable, hiding valid neighbours. That cuts directly against the telos.
   - It also contradicts the runbook line that "a source can be unavailable even while its committed inventory is readable".
2. **A forged reply signature makes a scope silently vanish from the catalog** (probe 05).
   - `SignedReply::verify` returns `AccessLimited` on a bad signature (`evidence_service.rs:324`). The catalog drops that error silently (`src/evidence_library.rs:54`), so the response is 200 with `scopes:[]`, indistinguishable from revocation.
   - This contradicts "Missing evidence is never silently skipped". Disclosure still fails closed.
   - The reverse problem: one unreachable scope makes the entire catalog return 503.
3. **Stale clicks during a scope switch read the wrong scope** (probe 07).
   - Changing scope sets the new pin immediately, but the old rows and the Next button stay live until the new page arrives (`app.js:87,64-68,89`).
   - Clicking a scope-A row then sends `{pin:B, sequence:3}`, so scope B's occurrence 3 appears beside scope A's list. Provenance does show scope B, so nothing leaks, but the content is misattributed. Next also sends A's offset under B's pin.
4. **Four idle sockets lock everyone out** (probe 05).
   - The server allows four connections and drops the fifth (`evidence_library.rs:168-181`). With four idle sockets open, `GET /` fails in under 1 ms, and the slots only free when the 5 s header timeout expires.
   - Any local process can repeat this to keep the reader unavailable. A browser's parallel asset loads can plausibly hit the same cap.
5. **Reader principal separation is documentation only.** `Reader::new` accepts the storage service's own key as the reader signer (`evidence_reader.rs:96-122`; probe 05).
6. **The capability matrix in REQ-7 isn't really there.** The API returns `capabilities` and `unavailable`, but `app.js` ignores both. The UI shows a static sentence inside a collapsed `<details>` in `index.html`.
7. **Smaller issues:**
   - "Every request contacts the service" isn't quite true: out-of-range sequence or offset is answered locally even with the service down. Nothing is disclosed.
   - The token comparison isn't constant-time.
   - rustfmt leaves several overlong lines unformatted (`evidence_library.rs:35,175-181`; `evidence_reader.rs:234-235`), so the fmt check passes without actually checking them.
   - A source read makes two sequential remote calls with 30 s timeouts each, and the catalog up to 16, against a 35 s connection deadline.
   - Bidi control characters stay in the UTF-8 view, which allows display spoofing only.

## Findings

1. **BLOCKING — a full journal stops proxy restart, which stops inference.**
   - Probe `probe_full_journal_blocks_reporter_startup`: realistic attempt rows fill the 8192-page cap at about **79,740 attempts**, so the documented 100,000-attempt cap (`docs/V2-OPERATIONS.md:63`) can never be reached.
   - There's no expiry and no erasure command, and every process start inserts a session row (`src/evidence_operations.rs:271`).
   - After about **90 more restarts**, `reporter()` fails with "database or disk is full". `src/bin/kan-v2.rs:874-875` turns that into a startup error, so the collector or gateway won't start.
   - The direction is backwards: a telemetry store's capacity stops inference.
   - Fix: on any journal failure at startup, start anyway with a degraded reporter that counts everything as lost or falls back to stderr.

2. **BLOCKING (paired with 1) — a brief journal lock stops archive delivery.**
   - Probe `probe_journal_lock_stops_archive_worker`: holding a lock on the journal for 1.5 s makes `drain` exit with `DatabaseBusy`.
   - Cause: the journal's busy timeout is only 100 ms (`:122`), and every `save_worker(...)?` at `:317,329,336,349` exits the worker on failure.
   - The behaviour is documented (`V2-OPERATIONS.md:72`), but the shipped systemd example (`StartLimitBurst=5` within `StartLimitIntervalSec=60`, `RestartSec=5`) puts the unit into a permanently failed state if the lock lasts longer than about 25 s.
   - That couples derived observations to delivery of raw evidence. Telemetry write failures should be counted and retried; they shouldn't end delivery.

3. **Major — REQ-5's per-peer limit has no runtime coverage.**
   - Mutant M3 removes the eight-per-peer cap entirely (`src/evidence_gateway.rs:499`), and all 17 gateway tests still pass. So did M1 (no IPv6 /64 grouping), M2 (no IPv4-mapped normalisation) and M4 (global cap raised to 64).
   - AC-5 asks that a "delayed legitimate handshake from a **different** peer" survives churn. The test uses the same 127.0.0.1 peer for both the legitimate client and the flood (`tests/evidence_gateway.rs:1399-1402`), so it only proves "no eviction", not per-peer isolation.

4. **Major follow-up — the telemetry queue drops the newest state during normal streaming.**
   - Probe `probe_streaming_rate_drops_with_healthy_journal`, on a healthy, unlocked journal: 1500 updates for one attempt produced **1193 counted as dropped**, and one run persisted `observed=1468` instead of 1500.
   - So the latest cumulative snapshot itself can be lost, and per-attempt unconfirmed counts (including the "Gaps only" filter) can undercount.
   - The global loss warning still fires, so this never claims false completeness. But the dashboard can effectively never show "current", which trains operators to ignore the warning.
   - Suggested fix: keep only the latest snapshot per attempt instead of a FIFO queue.

5. **Other mutant survivors (tests too weak):**
   - Operations: M5 (retry backoff removed), M6 (nonempty-since reset every iteration), M7 (session reads as clean after a crash), M9 (no page cap on reopen), M16 (unclosed sessions always zero), M18 (owner-only permission check removed), M21 (channel overflow not counted).
   - Dashboard: M11 (duplicate Authorization headers accepted), M13 (non-loopback check removed from `serve`; the CLI still checks it).
   - UI: M22 (stale-reporter warning disabled).
   - M8 (blocking `send`) hung the suite until the 180 s bound. That's a timeout, not a kill.
   - Killed: M10, M12, M14, M15, M17, M19, M20.

6. **Minor:**
   - `CLAUDE.md:69` still says "One surface… No second/third UI". The exception is recorded only in `.design`, with no ADR.
   - AC-6 asks for supervisor arguments to be validated against CLI help, but nothing automates that. I checked by hand: they match, and `plutil -lint` passes. Templates exist only for the drain worker.
   - The idle worker does a fully-synced write every second.
   - Eight idle local sockets block the dashboard for about 5 s (a 9th client is closed immediately); the docs treat local users as trusted.
   - The token comparison isn't constant-time.
   - The busy flag can delay a reconnect after Lock until the next 5 s poll.

**Verified as working:**
- **Dashboard boundary** (12 hostile raw-HTTP cases): missing or `localhost` Host, `null` or `https` Origin, duplicate or lowercase or prefix-truncated tokens, OPTIONS and HEAD, path traversal were all refused. An absolute-form request returned 200, which is harmless because Host still has to match.
- **Missing journal:** the API returns 503 rather than zeros.

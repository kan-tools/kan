# Correction review: a95f28f vs e71cdf8

## Verdict: **BLOCK** (one hunk only)

The five test pins, the retry-styling fix, the doc change and the `Demonstrated-by` trailer all hold up when run. The blocker is the CI fix to the contention test (`tests/evidence_capture_contention.rs:308-327`). It gives the test's background writer zero wait (`busy_timeout(ZERO)`) but still requires `assert!(held > 0)` at `:341`. Capture holds SQLite's write lock at about 92–100% of the moments the writer tries, so the writer often gets no window at all.

- **HEAD's version is flaky:** P4 failed with `assertion failed: held > 0` in 6 of 35 runs (5/12, then 1/20, then 0/3 in full-suite runs).
- **The old version wasn't, locally:** HEAD^'s helper passed 15/15 here.
- **CI will keep hitting it:** CI runs this test (`ci.yml:34`). CI's original failure took 5.54 s, which means the writer was already locked out for its whole 5 s wait on Linux. A writer that doesn't wait at all is likely to get zero windows there too. That part is an inference; I didn't run Linux CI.

Production code is unaffected. But a required CI job that passes or fails by luck pushes people to rerun until green, which undermines the evidence discipline the repo relies on. Under ADR-52 the fix for this hunk needs its own review round. Nothing else in the correction needs rework.

**Does the helper still show real overlapping contention and complete capture?** Partly. When the writer gets windows (1–6 per run), they fall inside capture's active span (230–1225 ms out of 0–1245 ms). Capture was complete in every run I checked (observed equals queued, 87 or 88). But the overlap is sparse and random. The "~9% duty" the test prints is false; the real figure is 0–2.3%.

WHAT THE CODE DOES (read)
- web/library/app.js:106-117 validateScopes. The value must be an array of 16
  or fewer entries. Each entry must be a plain object with a scope string of
  1..256 chars, unique, and a pin object whose request is a 1..8192-char
  string and whose reply is a plain object.
- app.js:118-125: catalog() clears the inspector, buttons, rows, scope options,
  scopes, pin, history, coverage, count, capability list and pager state BEFORE
  the rpc.
- app.js:126-130: validateScopes runs before renderCapabilities, before
  `scopes = value.scopes`, before any <option> is built, before the Library is
  unhidden, and before page(0).
- On throw, run() (app.js:36-41) locks when the Library is hidden (first
  login). Otherwise it clears the inspector and, since pin is null, clears the
  capability list and scope options and sets "coverage is unknown" with the
  className reset. So state is cleared before navigation and no page/source
  request is issued.
- The limits match the server. Scopes are 64-hex (evidence_reader.rs:109,117).
  There are at most 16 (evidence_reader.rs:97). Pin request is
  `unhex(&pin.request, 4096)` (evidence_reader.rs:178), so at most 8192 hex
  chars. Pin.reply is a SignedReply struct, i.e. a JSON object
  (evidence_reader.rs:65-70). No false rejection of server-valid output; probe
  PB1 confirms the boundaries 16 / 256 / 8192 are accepted.
- The service still re-verifies every pin (evidence_reader.rs:178-187). The
  client check is a fail-closed UI guard, not an authorization boundary.

P4 ACTUAL-WAIT ASSERTION — MEANING
- `spent` comes from Spool::with_capture_wait (evidence_spool.rs:278-317). It
  is the sum of sleeps inside the SQLite busy handler capture_busy
  (evidence_spool.rs:712-728), not elapsed admission time. Crypto/fsync are
  excluded, matching evidence_capture.rs:250-252 ("Charge actual SQLite
  busy-handler sleep").
- So `waited > 0` means the production admission path actually hit SQLITE_BUSY
  against the coordinated writer's BEGIN IMMEDIATE window and the busy handler
  ran. That is the claim the test previously only implied through timestamps.
- Wrapper fidelity (tests/evidence_capture_contention.rs:236-253):
  admit_with_wait passes `operation`, `frame` and `wait` unchanged to inner and
  returns `result` unchanged. It sends a copy of result.1 on a capacity-1
  channel only for the first window. admit() still forwards to inner.admit.
  Faithful by reading.
- Determinism of delivery: the send happens inside the capture thread before
  `.join()`, so try_recv after join is ordered (happens-before), not racy.

FLAKE IMPLICATIONS
- enqueue_generated takes TransactionBehavior::Immediate as its first SQLite
  action (evidence_spool.rs:391-395), before any crypto
  (evidence_delivery.rs:42-66). After the rendezvous, the capture thread only
  has to reach BEGIN IMMEDIATE (microseconds) within the writer's ≥5 ms hold.
- The new failure mode is: the capture thread is descheduled for more than
  about 5 ms between `locked.recv` and BEGIN IMMEDIATE, so spent is 0. This is
  possible in principle on a heavily oversubscribed CI host, but small.
- Measured with temporary instrumentation (restored), first-admission waited:
  - 10 unloaded runs: 6.04–9.07 ms.
  - 20 runs under 20 busy loops on 10 CPUs: 8.31–10.13 ms.
  - 30/30 pass; minimum 6.04 ms. No near-zero values.
- The pre-existing 100 ms cap and `locally_queued == observed` assertion are
  unchanged and carry their own (separate) load sensitivity.

**APPROVE WITH FOLLOW-UPS**
The commit does what it says. Malformed, duplicate, over-limit and over-count
scope catalogs are rejected before any option, scope authority or page request
exists, after a pre-rpc clear. The limits match the server, so no valid
response is refused. The new P4 assertion measures real SQLite busy-handler
waiting through a wrapper that forwards wait and result faithfully, and
compiled mutants of the lock, the wrapper and production accounting all fail
it. The gaps are small committed-test gaps (F1–F4) that my probes close. They
do not undermine the north star.

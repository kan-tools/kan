## Findings

1. **High, fix before any non-loopback exposure: unauthenticated clients can block the gateway.** A connection takes one of the 8 slots before the TLS handshake and can hold it for up to 15 s (`src/evidence_gateway.rs:440-455`); extra connections are closed.
   - My probe opened 8 idle TCP sockets. A valid mutual-TLS client then failed with "tls handshake eof", and the provider received zero calls.
   - An attacker can renew this every 15 s indefinitely. The collector has no fallback, so Claude Code just gets a 502.
   - The guide's own example uses `--listen 0.0.0.0:8443`.
   - The same pattern works locally against the collector: authentication happens only after headers are read.
   - The design does document the 8-slot behaviour, and this slice isn't a deployment, so I rate it a follow-up, not a BLOCK. Fix by separating handshake slots from authenticated-request slots, or limiting per peer.
2. **Medium, provenance: the gateway doesn't record the request it actually sends to the provider.** Its "request" metadata is a copy of the headers it received from the collector (`evidence_gateway.rs:299-303`). The headers it really sends, filtered plus the installed key, are built at `:304-326` and `evidence_capture.rs:509-510` and never recorded.
   - Probe: gateway request metadata names were `[content-type, accept, x-kan-exchange, host, content-length]`, with `omitted=[]`.
   - So nothing in the gateway's evidence shows that a provider credential was installed.
   - This only partly meets the parent's "observed provider exchange" and the harness design's "explicit omissions" (REQ-3, AC-2).
3. **Low, fidelity: two undocumented header rewrites.** `cache-control: no-store` overwrites any `cache-control` the provider sent (`evidence_gateway.rs:421-424`). A request with no content-type is sent to the provider as `application/octet-stream` (`evidence_capture.rs:509`).
4. **Low, independent witness: nothing outside Rust decodes the new event kinds.** The Python decoders reject `http-metadata`, `http-metadata-chunk` and `transport-link` (`scripts/verify_encrypted_capture.py:58-59`, `scripts/verify_capture_frames.py`). Gateway evidence is only checked by the crate's own decrypt and deserialise path.
   - The design's "KANC2 readers must preserve unfamiliar event variants" has no witness. `Event` rejects unknown fields and has no catch-all variant. Readers fail loudly rather than treating unknowns as absent, so nothing is lost silently.
   - The real Claude Code smoke test checks the requests the provider received but never inspects either spool.
5. **Low, test gaps.** These mutants all pass the committed suite; each was killed only by my probes:
   - TLS 1.2 enabled
   - slot count raised from 8 to 10000
   - duplicate-credential check disabled
   - 30 s body timeout raised to 3600 s

   The behaviour itself is correct at runtime: a TLS 1.2 client gets a `ProtocolVersion` alert.
6. **Low:** `enqueue_generated` lost the before-commit/after-commit fault-injection hooks that `enqueue_observed` has (`evidence_spool.rs:378-380` vs `386-428`). Crash-boundary tests can't target the capture path's enqueue.
7. **Scope, partial against the parent:** the "visible gap" is only JSON health on the proxy's stderr. Claude Code and the user's session get no signal. The harness profile also doesn't list source event IDs as the parent asks. Both designs state their exclusions honestly: OAuth, hook capture, deployment and migration are named as out of scope before implementation, not narrowed during it.
8. **Doc nit:** the harness design says `persistence.rs` and the surface TSV "remain unchanged". The range edits both (a comment and the design reference), as part of the gateway design's spool change. Harmless.

NEW FINDINGS (this round)

C-F1 [LOW-MEDIUM — design ambiguity on the replay side. MUST be resolved before replay consumes this component.]
- The member now distinguishes authenticated from unverified lengths, but the downstream codec rules still say
  "known":
  - codec :112-113, `restored`: "Any known expected lengths must agree; conflicting references refuse"
  - codec :139, R1: "Each must verify against its content address and all known expected lengths"
  - codec :147, output union: "verified bytes of all known expected lengths"
  - codec :129-130 says unavailable entries match "authenticated expected coordinates", although the vector
    now also contains UnverifiedMembership coordinates.
- M1 and the proposed member_membership table (codec :216-217) still hold the claimed partial-copy lengths.
- A replay/restoration implementer reading "known" from the membership rows would constrain a candidate with an
  unauthenticated length. That contradicts codec :180-181 ("An unverified membership length neither classifies
  original bytes nor constrains a restoration candidate").
- Separately, codec :111-112 lets a `restored` target be any "original membership" key. In an incomplete copy
  that includes fabricated rows (RP02 / the fixture "partial-membership-fabrication-remains-unverified"). The
  text does not say that a restoration against an UnverifiedMembership coordinate carries that basis forward.
- Required:
  - Define every "known expected length" in restored/R1/output as the member-derived coordinate length, i.e.
    Loss/coordinate expected_length (authenticated only).
  - State that a restoration inherits and exposes the coordinate's recomputed basis.
- Not a member-code defect, but it is precisely the consumer contract.

C-F2 [LOW — test gap in the newly added code. Resolve before replay recomputes and signs loss vectors.]
- The clearing loop's `!c.referenced` condition (src :447) is what keeps issuer-authenticated lengths on
  IssuerMetadata losses in incomplete copies.
- Mutant M07, which clears every coordinate, passes all 40 author functions and the Python fixture. Only
  reviewer CP11 kills it (IssuerMetadata losses lose expectedLength).
- The fixture has no partial-copy case with an occurrence loss. "partial-profile3" has none, and
  "partial-membership-*" has only null coordinates. It also has no VerifiedCopyRecipe loss at all; Rust rp01
  covers that.
- The consequence would be a wrong signed `unavailable` wire for every missing retained request in a partial
  copy.
- Required: add a partial-copy occurrence-loss vector to the Python oracle and fixture, and a Rust assertion
  (CP11 can be promoted as-is).

C-F3 [LOW — test gap]

  author fixture only tests MAX_REQUEST+1.

  false refusal.
- Promote CP01 (MAX_REQUEST accepted with bytes missing).

C-F4 [LOW — residual early-detectable impossibility, the same class as A-F1/A-F3]
- A reference to the empty-bytes CID with a signed length ≥1 is accepted as a permanent Missing loss when the
  empty row is absent (CP03), and refused when it is present (RP14b).
- Nothing other than the empty string hashes to that CID, so no candidate can ever satisfy both CID and length.
- Moreover, SignedRequest::decode (src/evidence_service.rs:239-245) can never accept empty bytes, so an
  empty-CID SERVICE-REQUEST reference is unsatisfiable at any length.
- The A-F3 rationale ("cannot be satisfied, refuse even when bytes are missing") applies equally.
- Recommend refusing a service-request reference to the empty-bytes CID outright, in both implementations.
  Alternatively, record explicitly that it stays an unrestorable Missing loss.
- Not blocking: the loss is honestly unrestorable, nothing consumes it, and publication re-verifies.

C-F6 [INFO — the documented behaviour is consistent; recorded for consumers]

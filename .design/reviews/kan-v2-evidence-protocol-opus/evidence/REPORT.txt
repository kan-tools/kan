3. Concrete protocol BLOCKERS (must be resolved before implementation)
-----------------------------------------------------------------
B1  The fixtures do not support the proposed chain bindings. The design claims they do.
    Evidence: C3, mutate_oracle.log. With each verify() assertion deleted in turn, `--check`
    still PASSES for:
      chain commitments (attestation_vectors.py:118), chain position/scope (:117),
      genesis rule (:114), sequence arithmetic (:109), purpose allow-list (:112),
      scope length (:106), closed statement body (:103), profile v/kind (:101),
      record-CID shape (:91), and envelope bound (:95; it is masked because "oversize" is also
      "trailing").
    Only low-S, pinned-issuer and closed-envelope are killed. Every one of the "20 negative
    checks" (lines 142-167) mutates signed content WITHOUT re-signing. Each is therefore
    rejected by the signature, or by decoder framing, and never exercises the field or chain
    rule it is named after.
    The fixture JSON also contains only `positive` rows. The negatives are generated inside
    Python, so a Rust implementation has no negative vectors to consume.
    C2 shows the oracle's verify() logic does reject chain attacks once they are re-signed with
    the pinned key (P1: wrong previousAttestation/previousManifest/sequence/previousSequence,
    and non-null genesis). The logic is present; the gate does not exercise it.
    Contradicts: design :96-97 ("Independent codec fixtures must … reject noncanonical/
    duplicate/unknown fields"), AC-2 ("Removing attestation binding fails a named assertion"),
    and RFC :155-158 / design :199-201, which present the 20 negatives as chain/profile
    coverage.
    Required: commit re-signed negative vectors to the JSON, each labelled with the exact
    check it must trip and its error class. Cover: wrong previousAttestation, wrong
    previousManifest, skipped sequence, previousSequence ≠ sequence-1, non-null genesis,
    null predecessor at sequence>1, scope change mid-chain, configured-scope mismatch,
    unknown body field, v=2, unknown purpose, DER signature, r=0, s=0, s=n/2+1, non-P-256
    did:key, noncanonical did:key, verificationMethod mismatch, non-static identityVersion,
    CID-shaped bytes, nested-statement trailing bytes, and statement-level size.
    Make --check assert the specific failure label, not just any exception. The oracle
    currently catches (AssertionError, ValueError, InvalidSignature) indiscriminately
    (:155-161). Re-run mutate_oracle.py: zero survivors is the bar.

B2  The issuer model for upgraded chains is internally contradictory.
    - RFC :129-131: "an explicit upgrade preserves the historical receipt issuer and
      distinguishes the present verification issuer". This implies the upgrade signer can
      differ from the receipt issuer.
    - Oracle verify (:104-105) and RFC :121-122 pin ONE configured issuer per chain.
      P5 (C2) confirms that a chain cannot change issuer: "reject(pinned issuer)".
    - The existing reader pins one `issuer` per scope (src/evidence_reader.rs ScopeAccess)
      and requires receipt.issuer == that issuer (decode_record).
    - After an upgrade, new `admitted` statements must come from the service key
      (RFC :129: "New admission requires the current receipt issuer"). They chain after
      `retained-verified` statements.
    So either (a) the upgrade signer MUST be the live service key, or (b) the profile allows
    distinct receipt-issuer and attestation-issuer configuration, or issuer transitions.
    (a) puts the service private key into an offline CLI. Design :194 says no key-placement
    preference is selected, which contradicts :202 ("No unresolved owner preference blocks
    that technical pass").
    (b) requires new reader configuration, a new chain rule and new fixtures.
    Neither is specified. The fixture's retained-verified row uses receipt issuer ==
    attestation issuer, so the "distinct verification issuer" case is never exercised.
    Also unspecified and unfixtured:
      - `admitted` requires receipt.issuer == statement.issuer. P4 accepts an `admitted`
        statement over a foreign-issuer receipt.
      - The statement's receipt CID must decode to a receipt that structurally binds the
        statement's manifest. P3 accepts a statement whose receipt belongs to a different
        manifest, because the oracle never decodes receipts.

B3  Snapshot linkage for paginated reads is not specified, and the statement carries no
    archive-instance or epoch identity.
    The chain is backward-linked (previousAttestation). A reader pinned at (N, tip, S_N) can
    link page rows k..k+40 to the pin only by also fetching and verifying S_{k+41}…S_N, or by
    verifying the whole chain from genesis. P6 shows verify() cannot validate a mid-chain row
    without the verified predecessor.
    REQ-4/design :127-129 ("independently verifies issuer proofs and snapshot linkage before
    exposing any row") is O(N) ECDSA work per pin as written. Implementers will be pushed to
    check per-row signatures only.
    Per-row signatures are not enough, because legitimate same-issuer forks are reachable
    under this design. P2 shows a second, different, validly signed statement at sequence 2
    with the same predecessor verifies. Forks arise from:
      * restoring a profile-2 backup (Ledger::backup) and resuming admission: the same
        sequence numbers are re-signed with different manifests/issuedAt;
      * running the copy-upgrade twice to two fresh destinations with the same signer
        (resume binding only constrains ONE destination);
      * two service partitions with the same scopeToken and issuer.
    RFC 4 Terminology (:26) already requires a frontier "bound to an archive instance". The
    statement has no such field, and InventorySnapshot (through, tip, attestation) does not
    add one.
    Decide before freezing bytes:
      - add an archive-instance/epoch identifier, and/or an accumulator, to the statement.
        This changes the pinned bytes and CIDs;
      - specify the page-verification algorithm (descending-from-pin pages; a
        reader-verified chain cache with stated trust status; or a cumulative commitment);
      - state whether readers keep a per-scope monotonic pin to detect rollback/truncation.
        That would be new persistence with a surface row, not an access grant.
      - say explicitly that a single issuer can equivocate and that no signature here
        detects it across readers.

4. Non-blocking findings (follow-ups that must land with the implementation)
-----------------------------------------------------------------
F1  The P-256 restriction is not provided by the reused verifier.
    src/sign.rs:1854 `verify` → atrium-crypto 0.1.3 verify.rs:68-69 dispatches BOTH P256 and
    Secp256k1. High-S IS refused by default (verify.rs:84-90, allow_malleable=false), and DER
    is only parsed when malleable. The design's "reuse pinned did:key machinery" therefore
    needs an explicit multicodec 0x1200 check, or a configured secp256k1 issuer will verify.
    Signing (keypair.rs:75-77) normalises low-S. It is RFC 6979 via try_sign, so Rust can
    reproduce the fixture signatures exactly. Assert that in parity.
F2  The proof-profile Append output and the client spool-release rule are not framed.
    Today admitted_manifest (src/evidence_service.rs:352-377) releases on the receipt only.
    Decide:
      - Is the proof carried in Committed and required for release?
      - Does a retry of a pre-upgrade operation return `retained-verified`?
      - Must a client accept that purpose? If not, its spool never drains.
F3  Degraded mode entry is unspecified. Service::new → audit_suffix → read_signed fails on
    any missing object (evidence_service.rs:481, 672-675), and Ledger::open → verify() reads
    every object (evidence_store.rs:608, 1000).
    Decide:
      - Is the read-only inventory server an explicit operator mode or an automatic fallback?
      - Which process serves InventorySnapshot/Page when the writable Service cannot start?
      - Are integrity and unavailable states disclosed only after scope/grant checks, so that
        unknown principals keep the access-limited shape (REQ-3)?
F4  Legacy RecoveryReader::rebuild recreates SCHEMA v1 (evidence_store.rs:263). Any new
    rebuild/backup verification that forgets the proof table silently drops proofs.
    Profile 2 MUST change user_version: legacy check_schema refuses only on version≠1
    (:620), and RecoveryReader does not run check_write_schema. A profile that kept
    user_version=1 and added a table would be read by old recovery and silently lose proofs.
    Pin this as a test.
F5  Metadata-only recovery output has no declared format or marker. Strict verify_file
    (:1085-1092) rejects missing objects, so the "payload-incomplete" label must be durable
    in the output (surface row and report), not just CLI text. The output must be unable to
    pass the evidence_restore full contract or Ledger::open.
F6  Legacy-copy honesty is sound, but it narrows the motivating case. A legacy archive
    with any missing payload can never be upgraded (design :168-170, REQ-5). Already-damaged
    legacy archives therefore gain no payload-independent browsing. That is honest and was
    decided before implementation (legitimate narrowing), but the owner should be told
    explicitly. Prefix-only upgrade (through < first loss) is neither specified nor
    forbidden; decide it.
F7  Profile-2 raw `Ledger::commit` / `commit_partition` (no proof) must be refused at the
    type level, not just detected later. Specify the chain's scope rule as partition-only:
    the oracle requires scope equality across the chain, but Ledger::commit permits
    multi-scope archives (evidence_store.rs:709-726).
F8  The statement-level size bound and the envelope 16 KiB bound interact with the existing
    65,536-byte decoder limit (scripts/evidence_reference.py decode). State that the nested
    statement must decode under the 16 KiB envelope cap. Python and Rust must enforce it in
    the same order.

10. Verdict rationale
-----------------------------------------------------------------
**BLOCK** (design readiness only). The direction is right and consistent with
telos/raw-data-and-projections:
  - loss is a sampled, labelled projection;
  - strict writable verification is unchanged;
  - upgrades are present-time and non-destructive;
  - atomic proof insertion has a clear hook in the existing immediate-transaction fence.
But the gate's own preconditions are not met:
  - The independent fixtures do not actually exercise the chain/field bindings: 10/13
    removal mutants survive, and the JSON has no negatives a Rust implementation can consume.
  - The issuer model for upgraded chains contradicts the single-pinned-issuer verifier and
    reader, and resolving it is an unselected key-custody choice.
  - Snapshot linkage for paginated reads, and forks from backup restore or repeated upgrade,
    are unspecified. Fixing them may change the statement bytes that the fixtures now pin.
Implementing now would freeze bytes and storage tables around unresolved semantics.
Resolve B1-B3 (and U1-U3), regenerate and re-review the fixtures, then re-run this gate with
a fresh reviewer.

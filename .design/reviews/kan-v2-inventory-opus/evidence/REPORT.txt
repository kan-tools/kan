3. SCOPE A — Unicode/inode SQLite family correction (f656994)

Code read: src/evidence_store.rs:407-489.
- sqlite_paths gives the family: main + -journal/-wal/-shm.
- same_existing_file compares (dev, ino) after following symlinks.
- sqlite_name_eq compares chars after to_uppercase then to_lowercase; non-UTF-8 falls back to ASCII.
- sqlite_destination:
  - canonicalizes the destination parent;
  - refuses if any target-family path equals any source-family path by name model OR by existing
    identity;
  - then refuses `<base>-<suffix>` when the suffix matches a reserved name and <base> resolves to the
    source;
  - then refuses existing destination sidecars.
- Source paths are canonical at every caller:
  - RecoveryReader::open :190;
  - Ledger backup_copy :1209;
  - read_plan_for_copy copy_upgrade.rs:174.

Analysis: a target/source family collision can only be:
- main vs main (identity check);
- main vs sidecar, or sidecar vs main (identity when the main exists; otherwise the basename check
  against the existing source);
- same suffix vs same suffix (implies main aliases main).
Different reserved suffixes cannot alias each other ("journal"/"wal"/"shm" differ in length and
letters). So the remaining exposure is a filesystem alias spelling of a reserved suffix that the name
model does not equate.

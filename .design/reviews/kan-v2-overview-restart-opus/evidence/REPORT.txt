== 3. The fix (web/operations/app.js:125-126) ==
  before: key=s.last_job+':'+v.manifest_sha256
  after:  key=s.last_job+':'+JSON.stringify(v)
Correctness argument, checked against source:
 - The body renders only fields inside v: totals (8 counters, :127-128), sources.length, built_at
   and active (:129), and each source's generation/sealed_sha256/snapshot.digest (:130). Every one is
   inside JSON.stringify(v), so two samples that would render differently cannot share a key.
   Over-sensitivity (unrendered fields such as accounted_bytes, scan window, worker, or key order)
   only causes a harmless repaint with identical content (RP11 shows 1 rewrite, same text).
 - The label is recomputed on every accepted reply, before the early return (:123), so age and
   superseded state never depend on the key.
 - Stability: the server assigns `last` once per completed job and clones it on every status()
   (src/evidence_operations_collection/overview.rs:456-458, :500-502). serde emits fields in
   declaration order (Overview :72-84, Source :41-46, Scan projection.rs:24-30). Identical replies
   within one process therefore produce identical keys, and RP10 confirms no rewrites of summary,
   coverage or sources.
 - Reset paths: the key is cleared on last:null (:124) and on lock (clearOverview :99). A
   validation failure throws before overviewData/overviewKey change (:123), so the prior body stays
   and the label says "Invalid ... Prior sample retained." (RP9). Nothing after `overviewKey=key`
   can throw on validated input, so the key cannot be set over a half-rendered body.
 - Injection: still textContent only; no new sink.
Bounds (RP12, server-shaped fixture with every Rust field): validation caps sources at 1024
(:105, a 1025-source reply is rejected and the prior 1024-row body kept). The key at 1024 sources is
485,784 bytes, held in one string. Ten distinct 1024-source renders took 22.7 ms in Node. Unknown
extra fields are not rejected, so key size tracks reply size. r.json() has already materialized
that reply, so this adds no new exposure, only roughly 2x transient memory.
Restart premise: UPb needs the UI to miss the last:null reply between restart and rebuild (5 s poll
or a paused tab). If the UI does see last:null, the key was already reset before this fix. This
narrows when the bug occurs but does not make it unreal.

== 6. Abort-aware regressions (UPa-UPi) assessed on their merits ==
They do execute the real catch/finally races. The aborted promise's handlers run as microtasks after
the synchronous `++overviewSerial` (:137-139), the same ordering as a browser. UPa/UPi/A3 show the
guards matter. The harness simplifications are as follows. Abort does not reject an in-progress
json() (my RP8 covers that, and current code passes). Responses carry no headers or stream. Timers
are real, so the 8 s timeout path is never exercised (RP6 covers it). UPb's age assertion
/0s|1s|2s old/ depends on wall-clock time and could flake on a runner stalled for more than 2 s.
UPd records observed queue semantics (last action wins), not a requirement.

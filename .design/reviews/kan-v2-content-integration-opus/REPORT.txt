8. FINDINGS
-----------------------------------------------------------------------------
No BLOCK-level finding. No invariant violation: nothing is persisted, no subject is mutated, no cites are
fabricated, the pin never replaces a current authorized read, and every refusal returns no plaintext.

B-F1 [MEDIUM, fitness for purpose; tension with telos/performance-at-scale] Quadratic mapping charge makes
  Content refuse modest real-sized captures. map_citations charges sum(original)+sum(body)(+duplicates) for
  EVERY item (src/evidence_content.rs:218-237) because map_region revalidates the whole stream per call, and
  request items are deliberately coarse whole-body regions. With the 64 MiB budget that limits
  items x stream bytes to about 32 MiB: char_b5 refuses a 134 KB / 130-message request and a 73 KB / 500-delta
  SSE response, far below the 8 MiB input and 1024-item bounds. Multi-turn agent requests that resend
  history routinely exceed this, so on real archives Content will mostly refuse. Fail-closed, not unsafe.
  Follow-up: validate each stream's sources once per request (cache the verified segment table, or add a
  map_region variant over a pre-validated stream) and charge that once; then slice per item. Re-run char_b5.
B-F2 [MEDIUM, explicitness/honesty] Every Content budget, timeout, admission and cancellation refusal is
  Failure::Unavailable -> HTTP 503 with the fixed body, which the UI renders as "This response could not be
  verified. Retry, refresh the snapshot, or choose another scope." (char_u6; app.js:40-42). After
  authorization succeeded, telling a human that verified evidence "could not be verified" is wrong, and
  "retry" cannot help a deterministic budget refusal. This contradicts AC-3 "explicit refusal" and the design's
  "structured reason codes". Follow-up: a distinct non-disclosing limit status for post-authorization refusals
  (e.g. 413/422 + fixed code such as "content-limit"/"busy"/"cancelled"), mapped to its own UI wording.
B-F3 [LOW-MEDIUM, test adequacy] The two worker-side guarantees the prompt singles out are unpinned:
  B-M1 (drop the permit before the blocking worker runs) and B-M2 (render ignores the cancel flag) survive
  the author suite AND my probes; B-M4, B-M6, B-M9, B-M10, B-M11 and B-M12 (acquisition cap, overall deadline, request-wide citations/output/items, wired serialized cap) also survive everything. Code is correct as read; my timing probe char_b8 could not distinguish them (inconclusive method).
  Follow-up: a deterministic seam (like interpretation's interpret_observed) that pauses render after its
  first item, then asserts that dropping the request sets the flag, the worker exits with Unavailable, and the
  permit is unavailable until then.
B-F4 [LOW, evidence currency] The six retained backend controls cite tests/evidence_reader.rs:1557/:1597,
  which match the 82aaf58 test layout (content_rechecks at :1540), not bb1e0ab (:1565/:1588); bb1e0ab changed
  src/evidence_content.rs by 78 lines afterwards. The checkpoint text presents them as qualifying the provider
  v2 integration. .design/reviews/kan-v2-content-author/README.md is also stale (says provider 0d04848 under
  review, 34 UI tests, browser pending). Re-demonstrated here; correct the README/checkpoint wording.
B-F5 [LOW, explicitness] unexpected_starts (duplicate start events) and observed/expected byte extents are on
  the wire but never rendered. A response stream has no extent claim, so an interpreted response may be an
  observed prefix ending on an event boundary; only the absence of the coherent-stop line hints at it.
  Follow-up: render unexpected starts and "observed N bytes; extent unknown" for response streams.
B-F6 [LOW, UX] Interpret stays disabled after a Content request is superseded by a Source click until the
  selection changes (char_u1; app.js:222 disables, only updateSelection re-enables).

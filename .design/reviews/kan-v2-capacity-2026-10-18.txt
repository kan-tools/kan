## Findings (located)

1. **Medium – hitting the session cap stops all attempt recording.** `src/evidence_operations.rs` `session()`: the 1,025th reporter session (roughly one per gateway start, never pruned) runs `note_capacity_failure`, which seals the journal. After that every `record()` is refused until the owner rotates. The author's own test asserts this, and I reproduced it with a temporary probe (since deleted). The UI shows sessions as plain text and has no near-limit warning (`app.js` `journalState` only warns on pages). The design wording "independent attempt/session limits" doesn't clearly allow this coupling, so it needs a decision.
2. **Low–medium – a sealed journal does a durable write for every refused record.** `note_capacity_failure` rewrites the control row even when it's already exhausted. In my probe, 20 refusals bumped the SQLite change counter by 20 (about 13 ms each with fullfsync). Lost data is still counted, but it means steady fsync load and repeated rollback-journal attempts when the device is full.
3. **Test gaps (mutations that survived):**
   - M12: removing the "active must be the last, unsealed generation" check (`evidence_operations_collection.rs:111`) passes every test. A tampered manifest could then point writers at a sealed generation.
   - M16: never writing `last_success` passes every Rust test, even though REQ-1 names the persistence timestamp.
   - M15: skipping capacity marking on the worker write path passes.
   - M07 and M08 each survive alone, because the two lock layers back each other up. Mutating both together is killed.
   - M14: dropping the directory fsync after publication can't be detected without a crash harness.
   - UI: focus restore after refresh (U02), not re-announcing an unchanged notice (U05), and the future-clock guard on `last_success_at` (U07) are only covered by the author's browser notes, not by Node tests.
4. **Low – nothing stops the old file after adoption.** Adoption doesn't mark the source, and `ops-status health` still worked after `ops-adopt` (`cli-probe.log`). Avoiding split writes depends entirely on the runbook's reconfiguration step.
5. **Low – lock-file race.** `open_file` and `lock()` check the lock file with `symlink_metadata`, then open it with `File::open`, which follows symlinks. That leaves a swap window, limited to the owner-only directory.
6. **Low – the "persistence unknown" warning can flicker.** The UI treats persistence as fresh only within 5 s, but workers are allowed 45 s. A long `deliver_one` upload can briefly show the warning. It errs on the cautious side, not the dishonest side.

**What I confirmed in the code:**
- **Capacity:** the global count only changes under the shard lock, together with the matching insert or remove (`:307-331`), and the 256 bound uses an atomic compare-and-update, so it can't be exceeded.
- **Locking:** the writer takes one shard lock at a time (`:354-372`) and the callback makes a single bounded try_lock attempt, so neither can deadlock.
- **Wake and shutdown:** a wake is sent after every admission, and the writer drains the final batch on disconnect. `unclosed_sessions` was 0 in every run.

## Findings

- **F1 (medium): the retry budget is unproven.** With `ADMISSION_TRIES = 512` changed to `1`, every test passes (synchronized got 78–79/80 with 22–35 losses, inside the allowance of 4). Sharding alone carries the qualification. Collapsing to one shard fails the synchronized test only 2 of 3 times; only the private sharding test catches it every time. Since healthy runs score 80/80 with 0 losses, the threshold of ≥76 is loose. Don't cite this test as evidence for the retry.
- **F2 (low): the runner hides untracked files.** `scripts/revert_v2.py` stubs `ls-files` to return nothing. That suppresses the engine's "untracked and therefore NOT reverted" note: during my run `review-evidence/` was untracked and no note printed. Such files are copied into the export but neither reverted nor reported. It had no effect here because all production files are staged.
- **F3 (low): a timeout leaves the test running.** `subprocess.run(timeout=240)` kills only cargo. My probe showed the grandchild process survives (I killed it).
- **F4 (low): build isolation.** The author's retained logs were built in another worktree's target (`.worktrees/kan-v2-gateway/target`). Source export isolation holds; build-output isolation doesn't. The exports also land under `<root>/.local-state/reversion`, which is gitignored but inside the caller's tree, contrary to the docstring's wording.
- **F5 (low):** `tests/test_revert_v2.py` only tests result parsing. Export, the Git stubbing, compile-error classification and timeout have no tests (I checked those by hand, above).
- **F6 (nit):** the callback still allocates under the shard lock (`:317-318`, an `Arc::new` plus a clone). This existed in the parent too.
- **F7 (nit):** the barrier matches any `BEGIN DEFERRED` on the writer connection and stays set once tripped. That's record-specific today only because `record()` is the only transaction on that connection.
- **F8 (nit):** the loss counter also counts a failed initial session registration (`:431-435`) and a dead-writer wake (`:486-488`), which aren't strictly "health summary" losses.

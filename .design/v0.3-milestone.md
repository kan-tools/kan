# Feature: v0.3 — complete the relation surface, correct the status/knowledge split, organize the verb lexicon by AX phase

## Summary
v0.3 closes the two write-surface gaps v0.2's audit deliberately deferred
(#31: non-`SameAs` `RelationKind`s; #32: `Subject`/`SubjectKind`
construction), plus a genuine correctness bug this design pass found live
in kan's own dogfooded data (`kan issues` lists `spine` — a pure-knowledge
subject with zero `Status` claims — as an open issue). Getting there
required rethinking `Rejects`' data-model shape (it isn't a domain-semantic
relation the way `Blocks`/`About`/etc. are — it's `Retraction`'s
cross-author-aware sibling and belongs in that family instead) and giving
`SubjectKind` real behavioral weight instead of leaving it as inert
metadata. The resulting CLI/MCP verb surface is reorganized into four
AX-driven phases (Recording, Structuring, Correcting, Recalling) so the
verb list itself teaches an agent the intended workflow, not just a flat
alphabetical bag of commands.

`#27` (GitAncestry's O(n²) subprocess cost, now live rather than
theoretical since v0.2 populated real artifacts) rides along as a small,
self-contained, already-scoped fix. `#30` (real per-agent cryptographic
identity) was originally scoped into this milestone but is being split
out: it needs its own external research pass (SPIFFE/SPIRE-style
standards, atproto's agent-identity direction, revocation/rotation) per
its own issue text ("likely its own multi-milestone build-out... not a
single PR") — folding it in here would drown a well-converged, mostly-agreed
design under a mostly-unresearched one. Flagging this explicitly since it
was in the original scope selection, not silently dropped.

## Requirements

### Relation surface (issue #31)
- REQ-1: New CLI verb `kan relate <a> <kind> <b> [--cites <cid>...] [--file
  <path>]` (mirrors `kan same`'s existing shape exactly) writes
  `ClaimBody::Relation { kind, target: b }` for `kind` ∈ `{blocks, about,
  manifests-at, depends-on, accepts}` — 5 of `RelationKind`'s 6 remaining
  variants (see REQ-2 for the 6th, `SameAs`, staying under `kan same`).
  `RelationKindArg` (a `clap::ValueEnum`, kebab-case, matching
  `StatusValueArg`'s existing pattern in `src/cli/mod.rs`) is kept out of
  `src/claim.rs` for the same reason `StatusValueArg` is.
- REQ-2: `kan same` is unchanged and stays its own verb — not folded into
  `relate` despite the shape being identical. `SameAs` is the only
  identity-conferring edge (`docs/SPEC.md` §4.2) and the codebase already
  treats it with more ceremony than ordinary relations (the component-size
  guardrail, ADR-23's Anchor-vs-Anchor rejection); collapsing it into "one
  more `relate` kind value" would hide a distinction that matters
  elsewhere in the fold.

### `Rejects` gets its own shape, not a `RelationKind` (issue #31, the `Rejects` question)
- REQ-3: `RelationKind` (`src/claim.rs`) narrows from 7 to 6 variants —
  `Rejects` removed. `ClaimBody` gains a new top-level variant
  `Rejects { claim: Cid }`, structurally mirroring `Retraction { supersedes:
  Cid }` (`ClaimKind` gains a matching `Rejects` variant, sitting beside
  `Retraction` the same way `Retraction` already sits beside `Relation` —
  not nested inside it). Because no CLI/MCP path has ever constructed
  `RelationKind::Rejects` (confirmed: it's part of #31's premise), this is
  a zero-cost shape correction before any real data exists under the wrong
  one, not a migration.
- REQ-4: New CLI verb `kan reject <cid> [--file <path>]` writes
  `ClaimBody::Rejects { claim: cid }` — only when the target claim belongs
  to a *different* author than the caller; errors with a message pointing
  to `kan retract` when the target is the caller's own claim.
- REQ-5: `kan retract <cid>` (existing verb, unchanged behavior) gets its
  cross-author error message updated to point to `kan reject` by name.
  This is a message-only change — `retract` still only ever writes
  `Retraction`, never dispatches; the split into two verbs (not one verb
  with silent dispatch) is deliberate: no single call should have two
  possible fold-time meanings depending on facts the caller may not track.
- REQ-6: `fold::identity` gains `excluded_by_rejection(claims, trust) ->
  HashSet<Cid>`, a sibling to the existing `excluded_by_retraction` but
  **trust-gated** (unlike self-retraction, which is deliberately
  `TrustBase`-independent, per that function's own doc comment): a live
  `Rejects { claim }` claim excludes `claim` from a viewer's fold only when
  that viewer's `TrustBase` trusts the rejecting author (`docs/SPEC.md`
  §8: "a local suppression honored only by folds that trust the
  rejecter"). Threaded through both `fold::fold`'s general claim-visibility
  filtering and `identity::merge_classes` (a rejected `SameAs` witness must
  also stop contributing to identity computation for a viewer who trusts
  the rejecter) — the same two threading points `excluded_by_retraction`
  already has. A `Rejects` claim is itself an ordinary claim CID, so
  `Retraction`'s existing kind-agnostic `supersedes: Cid` already lets an
  author undo their own `Rejects` with no special-casing needed.

### `Subject`/`SubjectKind` gets real behavioral weight, not just reachability (issue #32)
- REQ-7: `kan observe`/`kan plan`/`kan decide`/`kan block`/`kan resolve`
  all gain optional `--title <text> --kind issue|idea|question` flags,
  required together (erroring clearly if only one is given — `ClaimBody::
  Subject`'s two fields are both non-optional, so there's no sensible
  partial write). When given, writes an additional `ClaimBody::Subject {
  title, subject_kind }` claim for the same subject, alongside whatever
  the verb already writes. `SubjectKindArg` (clap enum, kept out of
  `claim.rs`, mirrors `StatusValueArg`) maps to `claim::SubjectKind`.
- REQ-8: `actions::issues` (`src/actions.rs`) stops treating "no `Status`
  claim ever written" the same as "open." A subject is only listed when it
  has at least one live `Status` claim (any value — even `Unclassified`
  isn't the trigger, *presence* of the claim kind is) **or** its most
  recent live `Subject` claim declares `SubjectKind::Issue`. A subject with
  neither signal (the common case for pure-knowledge subjects) is excluded
  entirely. Confirmed as a real, currently-shipped bug, not a hypothetical:
  `kan issues` in this repo right now lists `spine` — kan's own
  dogfooding log, which has never had a `Status` claim and structurally
  never should — as an open issue.

### Narrative/status generalization
- REQ-9: `kan observe`/`kan plan`/`kan decide` gain an optional `--status
  <value>` flag. When given, writes a paired `ClaimBody::Status { value }`
  citing the narrative claim — the exact pairing mechanism `resolve`/
  `block` already use, generalized to any narrative kind and any status
  value instead of two hardcoded special cases. `kan block`/`kan resolve`
  are **unchanged** — their fixed pairing (`Blocker`→`Blocked`,
  `Resolution`→`Resolved`) stays hardcoded, since that pairing is
  inherent to what those two kinds *mean*, not a special case needing
  generalization. This closes previously-impossible-in-one-call
  combinations (e.g. `Decision` + `Status{Closed}`) without adding a verb
  per combination.

### Verb lexicon reorganized by AX phase
- REQ-10: `src/cli/mod.rs`'s `Command` enum is reordered into four
  declared groups — Recording (`observe`/`plan`/`decide`/`block`/
  `resolve`), Structuring (`same`/`relate`/`mark`), Correcting
  (`retract`/`reject`), Recalling (`show`/`status`/`issues`/`context`) —
  so `kan --help`'s output (clap prints subcommands in declaration order)
  reflects the phase structure with no runtime cost, purely from ordering.
- REQ-11: `KanServer::get_info()` (`src/mcp.rs`) instructions are rewritten
  around the same four phases, replacing the current flat kind-by-kind
  description, while staying factual/non-prescriptive (still guarded by
  the existing sequencing-language test in `tests/mcp_server.rs`).
- REQ-12: MCP tool surface mirrors the full CLI: new `relate`/`reject`
  tools; `observe`/`plan`/`decide` params gain `status?`/`title?`/`kind?`;
  `block`/`resolve` params gain `title?`/`kind?`.

### Ancillary: `GitAncestry` caching (issue #27)
- REQ-13: `relations::GitAncestry::relations` caches `is_ancestor` results
  within one `compute_all` pass (a `HashMap<(Sha, Sha), bool>` local to the
  call), since the same commit pair can recur across different
  merge-classes in one fold — the "obvious first optimization" `GitAncestry`'s
  own doc comment already names. Now live rather than theoretical: v0.2
  populated real artifacts on every claim (REQ-8/REQ-9 of
  `.design/v0.2-milestone.md`), so this cost is no longer hypothetical.

## Acceptance Criteria
- [ ] AC-1: `kan relate bug-42 blocks issue-7` (and the other 4 kinds)
      writes a live `Relation{kind, target}` claim; `kan show bug-42`
      reflects it. `same-as` is not a valid `kind` value for `relate`
      (rejected at argument parsing) — `kan same` is the only way to write
      `SameAs`, confirming REQ-2's exclusion.
- [ ] AC-2: `RelationKind` has 6 variants (no `Rejects`); `ClaimBody::Rejects`
      exists as its own variant alongside `Retraction`, not nested in
      `Relation`.
- [ ] AC-3: `kan reject <cid>` on another author's claim writes a live
      `Rejects{claim}` claim; on the caller's own claim, errors mentioning
      `kan retract`.
- [ ] AC-4: `kan retract <cid>` on another author's claim errors mentioning
      `kan reject`; on the caller's own claim, behavior is unchanged from
      today.
- [ ] AC-5: a `Rejects` claim from an author the viewing `TrustBase` trusts
      excludes the target claim from that viewer's fold; from an author
      the `TrustBase` does *not* trust, the target claim stays live for
      that viewer.
- [ ] AC-6: `kan observe bug-42 "fixed" --status resolved` produces two
      claims (`Observation` + `Status{Resolved}` citing it) — same pairing
      shape `kan resolve` produces, via a different narrative kind.
- [ ] AC-7: `kan observe bug-42 "x" --title "Bug 42" --kind issue` produces
      an `Observation` claim and a `Subject{title, subject_kind: Issue}`
      claim; passing only `--title` or only `--kind` errors clearly.
- [ ] AC-8: `kan issues` does **not** list a subject with zero `Status`
      claims and no declared `SubjectKind::Issue` (regression case shaped
      exactly like `spine`: only `Observation`/`Plan`/`Decision` claims,
      never `Status`).
- [ ] AC-9: `kan issues` **does** list a subject with a declared
      `SubjectKind::Issue` `Subject` claim even before any `Status` claim
      exists for it.
- [ ] AC-10: `kan --help` lists subcommands in the four-phase order
      (Recording, Structuring, Correcting, Recalling).
- [ ] AC-11: MCP `get_info()` instructions describe the four-phase
      structure and still pass the existing sequencing-language guard
      test.
- [ ] AC-12: MCP `tools/list` includes `relate`/`reject`; `observe`/
      `plan`/`decide` tool schemas show optional `status`/`title`/`kind`
      params.
- [ ] AC-13: `GitAncestry::relations` does not re-invoke
      `GitSubstrate::is_ancestor` for a commit pair already resolved
      earlier in the same `compute_all` call (verified via a call-count
      instrumented test double or an integration test with a merge-class
      shaped to force pair recurrence).

## Architecture
- `src/claim.rs`: `RelationKind` loses `Rejects` (6 variants remain).
  `ClaimBody` gains `Rejects { claim: Cid }`. `ClaimKind` gains `Rejects`,
  sitting beside `Retraction`. `ClaimBody::kind()` match arm updated.
  Confirmed zero-cost: `RelationKind::Rejects` has never been constructed
  by any shipped code path, so no existing log data references the
  removed variant (same "checked, not assumed" compatibility discipline
  as the v0.2 release notes in ADR-28).
- `src/fold/identity.rs`: new `excluded_by_rejection(claims, trust) ->
  HashSet<Cid>`, trust-gated (unlike `excluded_by_retraction`). Both
  `fold::fold` (`src/fold/mod.rs`) and `merge_classes` union this
  exclusion set alongside the existing retraction-based one.
- `src/actions.rs`: new `relate`/`reject` functions (mirroring `same`'s
  shape); `retract`'s error variant/message updated; `observe`/`plan`/
  `decide` gain `status: Option<StatusValue>` and `title: Option<String>`/
  `kind: Option<SubjectKind>` params, each conditionally issuing one extra
  `append` call; `block`/`resolve` gain `title`/`kind` params only (no
  `status` — their pairing stays fixed); `issues` filter rewritten per
  REQ-8.
- `src/cli/mod.rs`: new `Relate`/`Reject` `Command` variants; `Observe`/
  `Plan`/`Decide` (via `NarrativeArgs`) gain `--status`; all five Recording
  verbs gain `--title`/`--kind`; new `RelationKindArg`/`SubjectKindArg`
  clap enums (kept out of `claim.rs`, same pattern as `StatusValueArg`);
  `Command` enum reordered into the four declared phase groups.
- `src/mcp.rs`: new `relate`/`reject` tools + param structs; `Narrative
  Params` gains `status`/`title`/`kind`; `BlockParams`/`ResolveParams`
  gain `title`/`kind`; `get_info()` instructions rewritten around the
  four-phase structure.
- `src/relations.rs`: `GitAncestry::relations` gains an in-pass
  `HashMap<(Sha, Sha), bool>` cache for `is_ancestor` results.
- `docs/DECISIONS.md`: new ADR(s) for the `Rejects` shape correction (with
  the subject-vs-claim-target reasoning from this design pass), the
  four-phase verb reorganization rationale, and the `SubjectKind`/`issues`
  correctness fix.

## Open Questions
None blocking — every genuinely architectural question from this design
pass (the `Rejects` subject-vs-claim tension, `same`-vs-`relate`
consolidation, `retract`/`reject` dispatch shape, the status/knowledge
split, verb-lexicon organization) was resolved in conversation before this
doc was written. Implementation-time details (exact clap flag conflict
handling for `--title`/`--kind` requiring each other, exact `HashMap` key
shape for the `is_ancestor` cache) are ordinary engineering, not open
design questions.

## Out of Scope
- **Real per-agent cryptographic identity** (issue #30) — originally
  selected into this milestone's scope, split back out during this design
  pass: it needs its own external research (SPIFFE/SPIRE-style standards,
  atproto's agent-identity direction, revocation/rotation story) per the
  issue's own text, and would drown this milestone's otherwise
  well-converged design under a mostly-unresearched one. Stays its own
  issue, its own future `/design` pass.
- **`ClaimBody::Result`** (issue #41) — a third narrative-kind gap found
  live during this pass, never constructed, no issue existed until now.
  Deliberately not pulled in; filed as its own follow-up rather than
  scope-creep this milestone, matching how #31/#32 were themselves split
  out from v0.2.
- **Storage backend / `Transport` trait work** (issue #29's epic) —
  explicitly discussed and deferred: `docs/SPEC.md` §10 already sketches
  the `Transport` trait shape for when this is picked up; no code or even
  doc-only roadmap work lands in v0.3.
- **Deeper `GitAncestry` restructuring** (e.g. a full topological sort) —
  REQ-13 ships only the caching optimization `GitAncestry`'s own doc
  comment already named as the obvious first step; anything past that is
  its own future look if the cache alone isn't enough.

# Feature: v0.12 milestone — identity resolution, then media and the fold

## Summary

Four things accumulated onto "v0.12" during v0.11 and they form two clusters
that barely touch. Both are in scope; **Cluster A ships first**; and this
document's own first job is the fence, because v0.11 never had one.

**Cluster A — identity resolution.** Execute `.design/identity-resolution.md`:
three functions answering one question each, one precedence order, no side
effects during resolution. Plus the at-rest decision that opens it (below,
Resolved Q1) and role declarations becoming claims.

**Cluster B — media and the fold.** #164 (retire `.kan/overlay`; the index
becomes the aggregate with a medium per row), B1 (the origin-aware fold),
#131 + #92 (the `of` field and the `.claims/` format), #165 (a read pays a
full CAR parse before the index-freshness skip can help — 5.3s on kan's own
log).

### Why this can be larger than one cluster without being v0.11 again

v0.11 was ten requirements, five PRs, ~5,000 lines and five blocking review
rounds. The honest count here is comparable, so the difference has to be
structural rather than a promise to be careful.

It is this: **v0.11's requirements were designed during the milestone.**
v0.12's are executions of specifications that already exist —
`.design/identity-resolution.md` for Cluster A, `.design/medium-architecture.md`
REQ-2/REQ-3 for #164, an ADR-recorded decision for B1. The postmortem's
finding was that patching an unspecified space generates roughly one defect
per patch. The repair is not a smaller milestone; it is a specified one.

The fence below is what keeps that true, and it is binding: anything not named
in Requirements is out, including things that look adjacent and cheap.

## Resolved Questions

### Q1: What carries the non-interactive signing case? — **the ssh model**

Settled with Maxine. Recorded on `identity-architecture`
(`bafyreif7uahhdhq6rbviv5nvspfq4hxces34v5a4d7duetjcv25zaut3ke`); wants ADR-87.

`.design/identity-resolution.md` opened on "agent pattern vs status quo" and
treated the agent as an alternative to a key file. It is not one. In ssh and
gpg alike the key lives in an **encrypted file** and the agent holds the
*decrypted* copy in memory after one unlock, acting as a signing oracle. The
agent is not the storage layer.

Three layers kan has been making one mechanism do:

1. **At rest, encrypted** — a passphrase-encrypted file *or* a platform
   keystore. The keystore is an alternative to a passphrase, not a higher tier.
2. **In use** — the agent, caching one unlock per session.
3. **Non-interactive** — an unencrypted `0600` file, deliberately. A GitHub
   Actions deploy key is exactly this. This layer is part of the design.
   kan's error was never that `KAN_IDENTITY_FILE` exists; it is that it was
   implemented as *redefine this workspace's identity* (question 1) rather
   than *here is where the key is* (layer 3).

**The consequence, which inverts the spec's own sequencing: an agent is only
worth having if the key is encrypted at rest**, because its entire job is
caching an unlock. kan's key today is in the keychain or in a plaintext file;
in neither case is there an unlock to cache. So the agent question is
*downstream* of the at-rest question, and asking it first was backwards.

**#96 is a code-signing problem, not a keychain problem.** A macOS keychain
item carries an ACL of trusted applications; "Always Allow" keys the grant to
the calling binary's *code identity*. An unsigned binary gets a new identity
every rebuild, so the grant never matches again — #69 and #96 are one cause
with two issue numbers. Signed, notarized apps do not have it.

Established by reading the dependency: kan resolves `keyring 4.1.5` with
default features `["v1"]` → `apple-native-keyring-store/keychain`, the
**legacy file keychain**, which is exactly the store the trusted-application
ACL belongs to. The same crate ships a `protected` backend for the modern
data-protection keychain, which has no trusted-application list — but needs a
keychain-access-group entitlement and therefore a signed binary. *Unverified;
expectation is `errSecMissingEntitlement`.*

### Q3: Passphraseless by default, or prompt at init? — **passphraseless**

Settled with Maxine, and on structural grounds rather than as a preference.

The question presupposed an init flow that does not exist. **kan has no
`kan init`**: a workspace comes into being inside `Workspace::commit_identity`
(`src/workspace.rs:257`), immediately before the first append and after every
validation, while `Workspace::open` mints nothing and reads create nothing
(ADR-83). So there are only three places a passphrase prompt could go, and
two of them fail:

1. **Inside the first write**, where minting happens today — which blocks
   `kan observe` in CI, from `day` shelling out, and from the MCP server. Two
   existing comments already name this hazard for the keychain:
   `src/mcp.rs:392` — *"An MCP server is a long-lived process with no
   terminal, so a keychain prompt raised by a read is one nobody can answer
   (#96)"* — and `src/workspace.rs:358`, *"or block on a keychain prompt it
   has no business raising (#96)"*. It is #96's failure shape — a hang, not a
   failure — reintroduced deliberately on every workspace's first write.

   *Twice wrong before it was right, and both are recorded rather than
   silently fixed. The first draft presented a splice of those two comments as
   a single verbatim quote from one of them. The correction then MISQUOTED THE
   SECOND ONE — dropping "keychain" and substituting "a" — inside the very
   paragraph explaining why inventing quoted text is unacceptable. Both were
   caught by cold review. In a project whose invariant is that provenance is
   sacred, a quotation is a `cites` edge in prose: paraphrase freely, but what
   sits inside quotation marks is either the bytes or it is fabricated.*
2. **A new `kan init`** — a real design change, and it loses either way as an
   answer here. Mandatory means every non-interactive caller must run it
   first; optional means the first-write path still mints when init was
   skipped, so passphraseless is the default regardless *and* the state space
   forks, which is what REQ-6's table exists to shrink.
3. **`kan identity protect`, after the fact** — a human, at a terminal, on
   purpose. The opt-in REQ-3 already specifies.

`read_secret_line` (`src/cli/mod.rs:323`) is already the right primitive and
was spiked before use per CLAUDE.md's crate rule: echo-off on a TTY, a plain
stdin line off one, with the branch explicit *because* `rpassword` does not
fall back. That off-TTY branch means `echo "$PASS" | kan identity protect`
works, so a provisioning script can create a protected workspace without a
terminal — which removes the last argument for prompting at creation time.

An explicit `kan init` is wanted for its own reasons and is filed as **#173**,
sequenced after Cluster A. **#174** covers `kan config` list/set and a config
TUI, and records that the TUI deliberately overrides CLAUDE.md's "one surface"
rule.

## Requirements

### Cluster A — identity resolution (ships first)

- REQ-1: **Three functions, one question each**, per
  `.design/identity-resolution.md`'s "The shape this asks for" —
  `workspace_identity(kan_dir)` (pure; never creates, writes, or migrates),
  `signing_identity(kan_dir, selection)`, `create_workspace_identity(kan_dir)`
  (the only writer, refusing whenever `workspace_identity` returns `Some`).
  `existing_identity` and `load_or_create`'s tri-purpose behaviour go away;
  question 1 has exactly one implementation, used by reads and writes alike.
- REQ-2: **`KAN_IDENTITY_FILE` is a selection, not a redefinition.** A
  selection naming something absent is *always* an error — never a mint, never
  a fallback, never a substitution of another key.

  *Amended during implementation: the original text also said "selections
  validate against the role registry", following
  `.design/identity-resolution.md`. That was **tried and reverted**, and the
  measurement is the argument — requiring a selection to name a declared role
  took the suite from 41 failures to 78, because in the CI/`day`/agent
  workflow `KAN_IDENTITY_FILE` **is** the identity and the workspace never
  gets a `.kan/identity` of its own, so `workspace_identity` is `None` forever
  and every write after the first is refused as an undeclared second identity.
  It broke the configuration the variable exists for. ADR-77's property lives
  where it belongs — no identity is ever* created *as a side effect of
  resolution — and CLAUDE.md's "affordance, not enforcement" covers the rest:
  naming an existing key is asking, and undeclared authorship is surfaced by
  `kan identity authors` and narrowed past by `--trust roles` rather than
  blocked.*

  **A keychain that errors is not a fallback to a key file.** `v0.11` loaded
  `.kan/identity` when the keychain raised an error; `workspace_identity`
  returns the error instead. That is deliberate: ADR-53 *deletes* a plaintext
  copy that matches the keychain and keeps one only when it **differs**, so a
  surviving `.kan/identity` beside a live keychain entry is disproportionately
  the mismatched case — falling back would sign as a DID that is not this
  workspace's identity. "I cannot reach the keychain" and "the key is in this
  file" are different answers, and a fallback makes a workspace resolve
  differently depending on transient reachability, which is #170's disagreement
  class moved from across-paths to across-time.

  *This is also why `kan identity adopt` now retires `.kan/identity-id`
  alongside the seed. Without that, a surviving keychain pointer outranks the
  key adopt just wrote, and adopt reports "this workspace now signs and reads
  as that identity" while the keychain keeps signing — the adopt→restore dead
  end v0.11 rounds 2 and 3 found twice, which REQ-1's single precedence order
  would have reintroduced on both paths at once. Caught by the cold review of
  PR #182.*
- REQ-3: **The at-rest default flips** (Q1). A fresh workspace roots in a
  passphraseless `0600` seed file; the keychain becomes opt-in via
  `kan identity protect`; `kan identity unprotect` migrates a grandfathered
  keychain-rooted workspace out with one deliberate prompt. This restores
  ADR-55's "file-resident, requiring no prompt on any platform", which
  `Seed::create` (`src/sign.rs::create`) overrode on a #6 at-rest argument.
- REQ-4: **#170 closed** — one precedence order, shared by reads and writes,
  so `--trust me` and `kan identity did` cannot disagree on any layout.
- REQ-5: **Role declarations become claims** rather than `.kan/roles` file
  state — provenance, an author, revocation-by-retraction, `--trust roles` as
  a fold rather than a file read, and the registry where the resolver already
  looks. `.design/identity-resolution.md` calls this "probably the single
  highest-value change adjacent to this spec". Specified in
  `.design/role-declarations.md`.

  *This entry said "this repo currently holds the failure it prevents, a role
  key whose declaration does not exist." It no longer does — AC-9 closed it,
  and `.kan/` here holds no `roles` file at all. Corrected when REQ-5 was
  specified, by listing every such file on the machine rather than trusting
  the sentence: the entire known migration population is four rows in one
  workspace.*
- REQ-6: **The cell table, written down and tested.** Eight dimensions:
  `KAN_IDENTITY_FILE` (unset / naming an existing path / naming a missing one)
  × `.kan/identity` × **`.kan/identity-id`** × `.kan/seed` × `.kan/seed-id` ×
  keychain (off / reachable-with-entry / reachable-no-entry / errored) × a
  role entry × log empty or not, for reads and writes. Most cells collapse
  under REQ-3; the table records *that they collapse* rather than omitting
  them. Delivered as `.design/identity-resolution-cells.md`.

  *`.kan/identity-id` and the keychain's error state were both missing from
  this list in the first draft, and a cold review found four table rows
  missing — every one of them a cell where one of those two is the deciding
  input. An enumeration is only as complete as its list of dimensions.*

### Cluster B — media and the fold

- REQ-7: **#164 — retire `.kan/overlay`.** The index becomes the aggregate
  with a medium per row (`.design/medium-architecture.md` REQ-2/REQ-3). Also
  unblocks v0.11's deferred REQ-3, whose blocker was `Workspace::open` having
  to resolve an identity so `ingest_published` could sign overlay commits.
- REQ-8: **B1 — the origin-aware fold.** `TrustBase::trusts` takes
  `(author, origin)`. `Local` trusts a claim iff `origin == Log` **and** the
  author has written here; `Solo` and `PeerContested` trust by author alone,
  because naming a DID explicitly *is* the admission REQ-6 describes. Decided
  with Maxine during v0.11 and recorded on `identity-surface`.
- REQ-9: **#131 + #92 — the `of` field and the `.claims/` format.** Two actors
  publishing one subject must not collide on a filename, and deletion
  detection must be able to see the accidental case it was built for.
  Changes the tracked format, so it carries a migration row and a compat
  answer.
- REQ-10: **#165 — a read must not pay a full CAR parse before the
  index-freshness skip can ask whether it can skip.** 5.3s on this repo's log,
  measured and filed.

## Acceptance Criteria

- AC-1: **The invariant golden.** A single-author workspace with no roles and
  no foreign claims produces byte-identical `show`, `status`, `issues` and
  `context` output — human and `--json` — through every commit of the
  milestone (`tests/golden_reads.rs`). This is the case that must stay still
  while identity resolution, at-rest storage and the fold all move around it.
- AC-2: **The change-ledger golden.** The surfaces v0.12 *does* move — the
  `--trust` vocabulary, the overlapping-author case, `--trust me` with no
  identity, `.kan/` layout, `.claims/` layout — are frozen against the
  pre-change binary in `tests/golden_trust_and_identity.rs`. This fixture
  **is expected to change**; a diff is accepted only in a commit that names
  the requirement it belongs to.

  *Corrected during PR 1.* AC-1 originally said one fixture would pass
  unmodified through every commit, which is false here and was false when
  written: REQ-3 changes which files exist in `.kan/`, REQ-8 changes what the
  overlapping-author case folds, REQ-9 changes published filenames. v0.11
  could make the stronger claim only because `Solo` and `Local` coincide for
  a lone author. Asserting byte-identity over deliberately-changing surfaces
  would have forced the fixture to be regenerated on nearly every commit,
  which is how a golden becomes a rubber stamp.
- AC-3: **The testable plane of REQ-6's table is derived, not curated** —
  `tests/derived_cells.rs` enumerates the full product of the dimensions it can
  construct and probes both resolvers against every configuration, so a cell is
  covered because the loop reached it rather than because somebody listed it.
  The keychain-reachable plane cannot be derived (#96) and is hand-checked in
  prose, which is a stated limit rather than a gap to be closed by care.
  Alongside it, `tests/identity_cells.rs` keeps one named `#[test]` per chosen
  cell so **each assertion is verified by reverting its own hunk and checking
  that *that* test goes red** — the mapping checked, not the aggregate. Round 5
  of v0.11 shipped a test that did not test its own fix because the mapping was
  assumed.

  *AC-3 first said "every cell of REQ-6's table has an assertion", which was
  false in both directions: seven documented cells had none and could not, and
  the curated table was itself missing cells that two cold reviews found. The
  derived table is what makes the claim checkable — it caught a mutation
  (a workspace key outranking `KAN_IDENTITY_FILE`) that left all 43 curated
  cell tests green.*
- AC-4: A workspace created by this build raises **no interactive prompt on
  any platform**, in CI, in a container, and under `day` shelling out — with
  `KAN_IDENTITY_FILE` unset. This is REQ-3's user-visible claim and #96's
  practical close.
- AC-5: `kan identity did` and `--trust me` resolve the **same** identity on
  every cell of REQ-6's table, including this repository's own grandfathered
  layout (`identity-id` present, no key file, no seed). REQ-4's negative
  control is #170 reproduced and then failing to reproduce.
- AC-6: For REQ-10, reads and writes are **both** measured, before and after,
  by interleaving two binaries kept side by side rather than by a single-run
  A/B. v0.11 reported a read speedup while writes had silently doubled, and
  nearly reverted the correct fix because one run in one order gave the
  opposite answer.
- AC-7: For REQ-8, the test that matters is the **overlapping-author** case —
  an author with claims in both the log and `.claims/`, asserting the log ones
  fold and the file ones do not. Its disjoint-author predecessor —
  `.design/identity-surface.md`'s AC-6 — passed while the requirement was
  half-delivered. Frozen pre-change by AC-2, where the default view currently
  returns both claims at `excluded_by_trust: 0`.
- AC-8: For REQ-1, **resolution has no side effects, on either path**: `.kan/`
  is byte-for-byte identical — and equally present or absent — before and
  after any command that resolves an identity without creating one, and no
  file outside `.kan/` is created or has its permissions changed. Three
  distinct violations exist today and all three must go:
  `keychain_account` writing `.kan/identity-id` while resolving (the spec's
  Consequence 2, and how the ADR-77 guard came to fire on evidence its own
  invocation had just written); the migrate-and-delete on the write path
  (cells table row 24); and **a read** — `show --trust me` with
  `KAN_IDENTITY_FILE` set — creating `.kan/` and chmod-ing the named key
  (row 13, pinned by `a_read_that_resolves_an_identity_still_has_side_effects`,
  which this requirement must invert). And `create_workspace_identity` refuses
  whenever `workspace_identity` returns `Some`, with **no enumerated evidence
  set** to be blind or self-triggering.

  *The read-side violation was found by a cold review. AC-8's first draft
  named only `keychain_account` and framed side effects as a write-path
  property, which is exactly the assumption `src/sign.rs::signing_identity` states and
  `tests/write_guards.rs::a_read_creates_no_workspace` fails to test, because
  it points the variable at a path that does not exist.*
- AC-9: For REQ-2, a selection naming an absent path **errors on both the read
  and the write path**, mints nothing, and leaves no residue: no new key file
  anywhere on disk, no claim in the log. The negative control is the artifact
  this repository was carrying — a role key with no declaration — reproduced
  and then unable to be reproduced.
- AC-10: For REQ-5, a role declaration is a claim: it **carries an author**, and
  retracting it removes the role from `--trust roles` **with no file edited**.
  A role whose declaring claim is retracted cannot sign as a declared role.
- AC-11: For REQ-7, a write and the immediately following read compute the
  **same** index freshness key over an unchanged workspace, and foreign claims
  survive a write. Both halves are required: v0.11 found two projection bugs
  that hid each other, where fixing the key alone would have converted a cost
  into a wrong answer.
- AC-12: For REQ-9, two actors publishing the same subject produce **distinct
  filenames and both survive**, and `publish` does not rewrite every record's
  `of` — which is what made deletion detection blind to the accidental case it
  was built for (#92).
- AC-13: For REQ-10, a read against a fresh index **does not open the CAR at
  all**, asserted structurally rather than only by timing, so the property
  survives a machine fast enough to hide it.

## Architecture

Paths this milestone expects to touch:

- `src/sign.rs` — REQ-1's three functions, REQ-2's selection semantics,
  REQ-3's default flip. Crypto, seed derivation and recovery phrases are **not**
  touched (see Out of Scope).
- `src/cli/mod.rs` — `kan identity protect` / `unprotect`, role commands
  moving to claims (REQ-5).
- `src/fold/trust.rs`, `src/store/index.rs` — REQ-8's `(author, origin)`,
  REQ-5's `--trust roles` as a fold.
- `src/actions.rs`, `src/store/` — REQ-7's overlay retirement, REQ-10's parse
  ordering.
- `src/transport/git_tree.rs` — REQ-9's `.claims/` format.
- `.design/identity-resolution-cells.md` — REQ-6's analysis and the plane no
  test can reach; `tests/derived_cells.rs` plus
  `tests/fixtures/golden/derived-cells-unset.txt` and its three siblings — the derived table itself; and
  `tests/identity_cells.rs`, one named test per chosen cell against both
  resolvers.
- `tests/review_fixes.rs` — where fixes answering reviews land, per CLAUDE.md.
- `tests/fixtures/migration-expectations.tsv` — v0.11.0's rows get **confirmed
  or corrected** here, when v0.11.0 first runs as a historical writer rather
  than as the build under test.

## Out of Scope

The fence. Anything here is out even where it looks adjacent and cheap.

- **kan running an agent, or speaking ssh-agent's protocol.** Deferred with an
  explicit trigger rather than vaguely: build it when `kan identity protect`
  has enough adoption that typing the passphrase gets old. Before that there
  is no unlock to cache and an agent buys a socket.
- **Code signing, notarization, a Developer ID.** The real fix for #96/#69,
  and a distribution commitment rather than a code change. Its own decision.
- **The `protected` / data-protection keychain backend.** Blocked on the
  above. One timeboxed spike is permitted, for the sole purpose of closing it
  on evidence rather than assumption — because "why not just fix the keychain"
  will keep returning until it is.
- **ADR-75's author→claim trust generalisation.** Origin-awareness (REQ-8) is
  a separate dimension and does not require building vouching.
- **UCAN, delegation, attenuation.** The thing to reach for if delegation ever
  crosses actors; beyond v1.
- **Sync, atproto, lexicons, PDS, relay.** The v1 fence, unchanged
  (`.design/sync-layer-architecture-and-staging.md`, ADR-35).
- **Incremental fold (#25).** Correctness before performance; REQ-10 is a
  parse-ordering fix, not a fold change.
- **#151's broader read-surface work** — a cheap change-detection primitive
  for per-turn consumers. REQ-10 takes the measured CAR-parse cost only.
- **`sign.rs`'s crypto, keychain *handling*, seed derivation, recovery
  phrases.** Five review rounds left these alone; this is the resolution layer
  above them.
- **TUI, web dashboard, editor extensions, a second UI of any kind.**

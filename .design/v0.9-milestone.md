# Feature: v0.9 milestone — durability you can use, and one root of trust

## Summary

Two tracks that ADR-35 had in separate releases, deliberately taken together.

**Durability.** v0.8 built `Log::ingest`, the verbatim-insert primitive a
restore needs (ADR-59), and stopped there: a repo can now *consume* another
actor's published tree but still cannot rebuild *its own* log from `.claims/`,
and `kan status` still cannot say which subjects would survive losing `.kan/`.
`.design/durability-log-recovery.md` REQ-2/REQ-3/REQ-5 are the user-facing half
of machinery that already exists.

**One root of trust.** `KAN_IDENTITY_FILE` is still the provisional per-role
identity mechanism (ADR-48/49), the keychain is still unusable
non-interactively (#96/#69), and kan has no encryption key at all — which the
sync roadmap needs before a remote can hold anything (ADR-54's L1/L2 rungs).
ADR-55 settled the architecture against a stated threat model; this builds the
half of it that does **not** touch the fold.

The pairing is not arbitrary. Both tracks converge on the same failure —
`.design/durability-log-recovery.md`'s "identity recovery gates log recovery"
(#93) — from opposite sides: a restore is only a restore if one escrowed secret
reproduces the exact signing DID, and that is precisely what the root work
establishes. Building restore against today's phrase and then changing what a
phrase derives would mean building the same wiring twice, which the durability
pass explicitly warned against.

## Requirements

### Durability

- REQ-1: `kan restore` rebuilds the local log from `.claims/`, reading every
  record via `GitTree::read_all_with_rev`
  (`src/transport/git_tree.rs`) and `Log::ingest`ing each record **whose
  author matches this repo's identity** into `log/repo.car`
  (`.design/durability-log-recovery.md` REQ-2). Foreign-authored records are
  the overlay's business and already handled (ADR-59); this is the same
  primitive pointed at the other destination.
- REQ-2: Restore **refuses, writing nothing**, when the local identity's DID
  does not match the author of the records it is asked to restore, naming
  `kan identity restore` and the recovery phrase as the fix
  (`.design/durability-log-recovery.md` REQ-3). This is "identity recovery
  gates log recovery" (#93) enforced at the one place it bites, and the #90
  failure made loud instead of silent.
- REQ-3: `kan status` gains a per-subject **durability state** —
  `unpublished` (lives only in `.kan/`), `published` (in `.claims/`, current),
  `stale` (published, but the log holds newer live claims) — computed against
  `git_tree::published_subjects`, surfaced in both the rendered output and
  `--json` (`.design/durability-log-recovery.md` REQ-5). Additive field, so
  `SCHEMA_VERSION` stays `1` under ADR-60's rule.

### One root of trust (ADR-55, the non-fold half)

- REQ-4: A phrase-derived, **file-resident seed** is the root: reproducible
  from the recovery phrase and requiring no prompt on any platform (ADR-55's
  Q1, where the impossibility triangle put REQ-3/REQ-4 ahead of
  non-extractability and accepted T5 as residual at the root). At-rest
  protection stays OS file permissions plus the existing keychain path where
  one is available — **not** the enclave, which cannot import an
  externally-derived key.
- REQ-5: A **derived X25519 encryption key**, per *identity*, derived
  independently from the seed rather than converted from the signing key —
  the textbook sign/encrypt split, which avoids the Ed25519→X25519 conversion
  footgun by construction. The signing key stays P-256 `did:key` (ADR-4,
  unchanged). Nothing in this milestone *encrypts* anything; the key exists so
  ADR-54's L1 rung and #7's HPKE protocol have a recipient to address.
- REQ-6: **Migration grandfathers every existing signing key** verbatim as the
  signing slot, so every existing DID and every signed claim stays valid. An
  existing identity becomes `{grandfathered signing key + new seed}`; only a
  newly created identity gets "one seed derives everything." This is the only
  form that makes the #90/#107 failure impossible rather than merely
  discouraged.
- REQ-7: The `WouldMintSecondIdentity` guard extends to the seed path, so a
  fresh binary meeting a seed-era workspace cannot silently mint a new DID —
  the same guard, on the new branch, before the new branch has users.
- REQ-8: `kan identity adopt` gives #90 the supported recovery path it asks
  for: a workspace whose keychain entry is unreachable or whose identity was
  superseded can be pointed at the right key deliberately, rather than by
  hand-editing `.kan/identity-id` from a stack trace.

## Acceptance Criteria

- [ ] AC-1: On a repo whose `.kan/` has been deleted, `kan restore` rebuilds
      the log from `.claims/` and every restored claim reads back through
      `kan show` with its original CID and author. **Negative control:** the
      restored `log/repo.car` contains only this identity's records — a
      foreign-authored record in the same tree lands in the overlay, not the
      log. (REQ-1)
- [ ] AC-2: Restore against a `.claims/` tree authored by a different DID
      exits non-zero, writes nothing (`log/` byte-unchanged, or still absent),
      and names the recovery phrase in its message. (REQ-2)
- [ ] AC-3: `kan status` reports `unpublished`/`published`/`stale` correctly
      for three subjects in those three states, in both the rendered output
      and `--json`; a `SCHEMA_VERSION`-pinning test confirms the field is
      additive. (REQ-3)
- [ ] AC-4: One recovery phrase reproduces both the signing DID and the
      X25519 encryption key, on a fresh workspace with no `.kan/` — asserted
      by deriving twice from the same phrase and comparing both, and by
      confirming the encryption key is **not** a conversion of the signing
      key. (REQ-4, REQ-5)
- [ ] AC-5: A workspace created under v0.8 opens under v0.9 with its DID
      unchanged and every prior claim still readable, gaining a seed without
      losing anything. **Negative control:** a fresh binary against that same
      workspace does not mint a new DID, and the guard fires if the seed path
      is asked to create one where an identity already exists. Run against a
      real multi-claim log, per ADR-52's rule that migration is proved on real
      data. (REQ-6, REQ-7)
- [ ] AC-6: `kan identity adopt` repoints a workspace whose identity is
      unreachable, and the previously-invisible claims become visible again —
      exercised on the state #90 describes, which v0.8 made *disclosed* but
      not yet *recoverable*. (REQ-8)

## Architecture

**Restore is `ingest` aimed at the other destination.** ADR-59 built the
primitive and `Workspace::open` already calls it for foreign authors; REQ-1 is
the same read (`GitTree::read_all_with_rev`) with the author test inverted and
`log/` as the target. The identity check (REQ-2) is the only genuinely new
logic, and it belongs *before* any write, so a refusal leaves nothing
half-restored. `kan restore` is a new verb outside the four CLI phases
(setup/tooling, like `identity` and `mcp`), not a claim-graph verb.

**The durability column is a fold-adjacent read, not a new claim kind.**
`published_subjects` (`src/transport/git_tree.rs`) already extracts the
`Publication`-bearing subjects; `stale` is that set intersected with subjects
whose newest live claim post-dates the published record's `rev`. It is a
column, not a nag — the same "make the gap data" posture as v0.8's
`excluded_by_trust`, and for the same reason: a state kan can compute should
be visible rather than enforced.

**The seed sits under the existing key resolution, not beside it.**
`sign::load_or_create` (`src/sign.rs`) keeps its resolution order; what changes
is that a workspace gains `.kan/seed` alongside the signing key, and a *new*
identity derives its signing key from that seed while an *existing* one keeps
the key it has. REQ-6's grandfathering means the two coexist permanently rather
than one migrating into the other — which is deliberate, because a migration
that rewrites a signing key is exactly the shape #107 proved dangerous.

**What this milestone does not touch, and why that makes it tractable.** ADR-55
carved the fold-touching half out already: two-layer signing (enclave-held
per-device sub-keys certified by the root) changes `AuthorId` and `TrustBase`
and is its own later milestone. So "Milestone 3" here is narrower than #30's
full text — root, encryption key, migration, guard — and none of it enters the
fold. That is what makes pairing it with durability reasonable rather than
reckless.

**Sequencing inside the milestone.** Durability first and landing on its own
PRs, because it is small, independent, and closes a live gap (#88/#93); the
identity track follows. The two touch different files almost entirely
(`actions.rs`/`git_tree.rs` versus `sign.rs`), so they should not contend. If
the identity half overruns, durability has already shipped and the release can
be cut around it — which is the mitigation for this being a larger milestone
than any so far.

## Resolved Questions

**Why not ship these as two releases, per ADR-35?** Because restore's
correctness depends on what a phrase derives (#93's "identity recovery gates
log recovery"), so building restore against today's phrase and then changing
the derivation would build the same wiring twice — the durability pass warned
against exactly that. Taken together, the identity work lands *before* anyone
has restored a log under the old assumption.

**Is this all of #30?** No, and the difference is load-bearing. ADR-55's
two-layer signing end-state — the part that closes T5 for signing, and the part
multi-device needs — touches the fold and stays a later milestone by that ADR's
own instruction. v0.9 builds the root and the encryption key; #30 stays open
after it, narrowed.

## Open Questions

<!-- OPEN: Q1 -->
### Q1: Does `kan doctor` ship here or later?

#90 asks for both `identity adopt` (REQ-8) and a `kan doctor` that reports
"N claims in the log, 0 visible under the current identity". v0.8's
`excluded_by_trust` note already delivers that specific sentence on every read,
which is most of what `doctor` was wanted for — so the remaining value is a
single command that checks several invariants at once (log/index/identity/
`.claims/` agreement) rather than one more disclosure.

**To resolve** when the PR breakdown is committed. Lean: **not here**. This
milestone is already two tracks, `adopt` closes the actionable half of #90, and
a diagnostic command wants to be designed against the failures people actually
hit rather than the ones anticipated — of which there is now a growing record.
<!-- /OPEN -->

<!-- OPEN: Q2 -->
### Q2: Does the durability column need a `kan publish --stale` companion?

REQ-3 makes staleness visible. The obvious next question is whether kan should
offer to fix it in one step, or whether `kan publish --all` (which already
refreshes every published subject) is sufficient.

**To resolve** in the REQ-3 build, once the column exists and it is possible to
see how often `stale` actually appears in real use. Lean: `--all` is enough,
and a second spelling for it is the kind of surface that accretes without
earning itself.
<!-- /OPEN -->

## Out of Scope

- **Two-layer signing / enclave-held per-device sub-keys** — touches the fold,
  `AuthorId`, and `TrustBase`; its own milestone per ADR-55.
- **The HPKE epoch/grant-history protocol and any actual encryption** — the
  HostedRelay/#7 pass (ADR-35 M1/M4). REQ-5 mints a recipient key; it does not
  use it.
- **`did:plc` migration** — the atproto pass (ADR-35 M5). REQ-8's `did:key`
  keeps that road open.
- **#121's default-trust question** — a separate design thread, and one whose
  inputs changed when v0.8 made foreign-claim consumption real.
- **The bulk read (#123)** — real, measured, and not durability or identity.
- **`kan doctor`** — see Q1.

# Feature: v0.4 milestone — Result reachability, index staleness check, subject-naming nudge

## Summary
Three small items, deliberately unrelated to `.design/sync-layer-architecture-and-staging.md`'s
epic, kept as their own release per ADR-35's version roadmap (v0.4.0-beta.1):
(1) issue #41 — `ClaimBody::Result` gets a dedicated `kan result` verb rather
than being removed as redundant, with sharpened tool-description verbiage
across `observe`/`result`/`resolve` so the narrowing semantic gap stays
legible to an LLM caller deciding between them; (2) issue #26 —
`Workspace::open` skips the full log-rescan + index-rebuild when a cheap
root-CID comparison proves nothing changed since the index was last built;
(3) issue #47's validated real-usage feedback — a proactive, non-blocking
naming-similarity nudge on write verbs, catching case/separator subject-name
variants (`f1-c1` vs `F1-C1`) before they silently fork a subject's history.

## Requirements

### #41 — `ClaimBody::Result` reachability
- REQ-1: New CLI/MCP verb `kan result <subject> <text> [--file <path>]
  [--verbose]` writes `ClaimBody::Result { text }` — `ClaimBody::Result`/
  `ClaimKind::Result` already exist in `src/claim.rs` and are already fully
  handled by `src/context.rs`'s `render_claim`/`kind_value` (no data-model
  change needed, purely a new write path, same "zero-cost, not a
  migration" shape ADR-29's `Rejects` reshape had). Bare narrative shape
  mirroring `resolve`/`block`'s positional `<subject>` (not `observe`/
  `plan`/`decide`'s optional `--subject`, since a Result is almost always
  about the specific subject the action targeted) — no automatic `Status`
  pairing, since a result doesn't necessarily resolve anything.
- REQ-2: `kan result`'s CLI help text and MCP `#[tool(description = ...)]`
  state its trigger condition explicitly: "the outcome of an action you
  just took," distinct from `observe`'s "something you noticed" and
  `resolve`'s "...and this closes the subject." `observe`'s and `resolve`'s
  existing descriptions (`src/cli/mod.rs`, `src/mcp.rs`) get the same
  sharpening, not just the new verb — the goal is legibility for an LLM
  caller given the fine semantic gap between all three, not just
  documenting the new addition.
- REQ-3: `kan result` joins the Recording phase group in `cli::Command`'s
  declaration order (`src/cli/mod.rs`, ADR-32's four-phase reorg) and
  `mcp::get_info()`'s Recording-phase description — same phase as
  `observe`/`plan`/`decide`/`block`/`resolve`.

### #26 — `Workspace::open` staleness check
- REQ-4: `store::index::Index` (`src/store/index.rs`) gains a `meta` table
  (`key TEXT PRIMARY KEY, value TEXT`) storing `built_from_root`, written
  inside `rebuild()`'s existing transaction (`let tx =
  self.conn.transaction()?`, `:53`) so the meta row and the claims table
  always commit atomically together — a crash mid-rebuild can never leave
  a half-updated claims table read back as "fresh."
- REQ-5: `Workspace::open` (`src/workspace.rs:69`) compares the log's
  current `HEAD` file content (`.kan/log/HEAD`, written by
  `store::log::Log` on every append, `src/store/log.rs`) against the
  index's stored `built_from_root`. When they match, skips
  `log.iter_all()` (which decodes and ECDSA-verifies every claim) and
  `index.rebuild()` entirely. When they differ, or the index has no `meta`
  row yet (fresh `.kan/` or a deleted-and-recreated `index.sqlite`), falls
  back to exactly today's unconditional full rebuild — no new correctness
  surface, only a skip when content-addressing already proves nothing
  changed.

### #47 — subject-naming similarity nudge
- REQ-6: A new normalization function (case-folding plus treating `-`/`_`/
  whitespace as equivalent separators) compares a write verb's target
  subject name(s) against every existing live subject's name (available
  via the same `fold::fold` view `subject_hint`, `src/actions.rs:697`,
  already computes). On a normalized match against a *different* literal
  spelling, prints a non-blocking stderr warning naming both spellings.
  Cheap, zero-new-dependency heuristic — not edit-distance/typo-tolerant
  matching (deferred, see Out of Scope).
- REQ-7: Fires on all 8 subject-taking write verbs: `observe`/`plan`/
  `decide`/`block`/`resolve` (Recording) and `same`/`relate`/`mark`
  (Structuring) — both the `a` and `b` subject positions for `same`/
  `relate`.
- REQ-8: Never blocks the write (affordance not enforcement, `CLAUDE.md`'s
  house rule) — exit code and the bare-CID stdout default are unaffected.
  CLI: stderr-only warning. MCP: the same warning text appended as an
  extra line to the tool's confirmation text (matching how `--verbose`/MCP
  already render richer output than the bare-CID default, `actions::
  AppendResult::confirmation`).

## Acceptance Criteria
- [ ] AC-1: `kan result bug-42 "ran the fix, build is green"` writes a live
      `Result{text}` claim; `kan show bug-42` reflects it; no paired
      `Status` claim is written (unlike `resolve`).
- [ ] AC-2: `kan --help` and MCP `tools/list` show sharpened descriptions
      for `observe`, `result`, and `resolve` that each state a trigger
      condition, not just a claim-kind name.
- [ ] AC-3: Deleting `.kan/index.sqlite` and re-running any read verb
      still reflects all claims (kan-spine's own AC-6, unregressed) — the
      missing `meta` row forces a full rebuild.
- [ ] AC-4: A test (mirroring `tests/git_ancestry_cache.rs`'s call-count-
      instrumented-double pattern) proves a second `Workspace::open` with
      no intervening writes skips `Log::iter_all`'s per-claim signature
      verification, while a `Workspace::open` immediately after a write
      still does the full rebuild.
- [ ] AC-5: `kan observe "x" --subject f1-c1` followed by `kan observe "y"
      --subject F1-C1` prints a stderr warning naming both spellings; the
      second write still succeeds (exit 0, claim written, stdout
      unaffected).
- [ ] AC-6: `kan observe "x" --subject f1-c1` followed by `kan observe "y"
      --subject f1-c2` (a genuinely different subject, not a
      normalization match) prints no warning.
- [ ] AC-7: The nudge fires identically on `same`/`relate`/`mark`, not
      just the 5 Recording verbs — including both subject positions on
      `same`/`relate`.

## Architecture
- `src/claim.rs`: **no changes** — `ClaimBody::Result`/`ClaimKind::Result`
  already exist (`:160`, `:125`, `:197`) and are already handled by
  `src/context.rs`. REQ-1 is purely a new write path.
- `src/actions.rs`: new `result()` function mirroring `retract`/`reject`'s
  shape (positional subject, no pairing) rather than `observe`/`plan`/
  `decide`'s (`--subject` optional, defaults to `"general"`). New
  `warn_similar_subject` (or similarly named) helper, called from every
  write function that takes a subject — REQ-6/7's normalization check,
  sharing the fold view each write already has available. `Index::rebuild`
  gains the `meta`-table write (REQ-4); a new `Index::built_from_root`
  reader and a small `Log`-side `current_head()`-style accessor (or reuse
  of the existing `HEAD`-file read path) back REQ-5's comparison in
  `Workspace::open`.
- `src/cli/mod.rs`: new `Command::Result` variant (Recording group,
  REQ-3), positional `subject`/`text` matching `Resolve`'s shape. Sharpened
  doc comments on `Observe`/`Result`/`Resolve` (REQ-2). Naming-nudge
  warning printed from `run()` after a successful write, using the new
  `actions::` helper's return value (a `Vec<String>` of warning lines).
- `src/mcp.rs`: new `result` tool + `ResultParams` struct, Recording-phase
  placement in `get_info()`. Sharpened `#[tool(description = ...)]` text
  on `observe`/`result`/`resolve`. Naming-nudge warnings appended to the
  confirmation string returned by write tools (REQ-8).
- `src/workspace.rs`: `Workspace::open`'s staleness-check branch (REQ-5) —
  the doc comment already flags this exact deferral ("incremental indexing
  is a later optimization once fixtures exist to guard it," `:78`); this
  milestone is that follow-through, though it's a skip-or-full-rebuild
  check, not incremental indexing itself (see Out of Scope).
- `src/store/index.rs`: new `meta` table + `built_from_root` get/set
  methods (REQ-4), inside `rebuild()`'s existing transaction.

## Open Questions
None — every question raised during this design pass (Result's verb vs.
removal, the staleness-check approach vs. true incremental indexing, the
naming-nudge similarity heuristic, its verb scope and output shape) was
resolved in conversation before this doc was written.

## Out of Scope
- **Edit-distance/typo-tolerant subject-name matching** — the normalized
  case/separator check (REQ-6) catches the one concrete failure mode
  reported (#47); edit-distance adds a real threshold-tuning risk (too
  loose and genuinely-different short subject names like `f1-c1`/`f1-c2`
  start false-positive-warning, which is actively harmful for a nudge —
  it trains agents to ignore it) and a likely new dependency
  (crate-trust-spike question, `CLAUDE.md`). Deferred until normalization
  proves insufficient in real usage, not guessed at now.
- **True incremental indexing** (appending new claims into the existing
  index rather than wipe-and-rebuild) — REQ-4/5's staleness check never
  does a partial index update, only skip-entirely-or-full-rebuild. Real
  incremental indexing is a larger, riskier change staying deferred, per
  `Workspace::open`'s own doc comment.
- **Anything sync-related** — this milestone is deliberately unrelated to
  `.design/sync-layer-architecture-and-staging.md`'s epic, per ADR-35's
  roadmap (each release stays one coherent theme).

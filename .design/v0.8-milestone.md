# Feature: v0.8 milestone — the reader, the trust surface, and multi-role

## Summary

Through v0.7, kan can *publish* a signed claim tree but cannot *read* one:
`GitTree::subscribe` exists with no caller and `Workspace` does not know
`Transport` at all (#97). Every trust mechanism past `Solo` is built and tested
in the library and unreachable from any surface. This milestone threads
`Transport` through `Workspace` so a published tree is actually consumed, ships
the `PeerContested` trust surface that makes another actor's claims visible, and
— validated by a field report from a real multi-agent research loop (#114/#115)
— makes multi-role operation against one workspace real rather than accidentally
blocked. It is the build the durability and identity design passes (ADR-54,
ADR-55) were sequenced to unblock: the reader is the exact machinery a durability
restore uses, which is why the design ran first.

The scope is grounded in what running the tool actually showed, not what the
issues assumed. Dogfooding two `KAN_IDENTITY_FILE` roles against one workspace
proved #115 does **not** reduce to documentation: the `WouldMintSecondIdentity`
guard (the #90 fix) *blocks* the second role's first write once the log is
non-empty, and even when both roles do append, `kan show` under the default
`Solo` trust displays only the active identity's claims — the other role's are
in the log, verifiable, and invisible. Multi-role needs a real write opt-in and
a real read surface, which is most of this milestone.

## Requirements

- REQ-1: `Workspace` threads a `Transport` so a published `.claims/` tree is
  read. `GitTree::subscribe` (`src/transport/git_tree.rs:843`, today with no
  caller) is wired into `Workspace::open` (`src/workspace.rs::open`) or an explicit
  read path, closing #97 (three ACs demonstrable only by linking the crate).
- REQ-2: A verbatim-insert primitive `Log::ingest` accepts a fully-formed
  `StoredClaim`, verifies its signature against the record's **own**
  `content.author.did`, and inserts it without re-signing — the primitive
  `Log::append` (`src/store/log.rs:689`, which re-signs with the local identity)
  cannot be. Destination is keyed on that signed author: same author →
  `log/repo.car` (restore); foreign author → a read-time overlay
  (`.design/durability-log-recovery.md` REQ-1/REQ-4).
- REQ-3: The `PeerContested` trust base is reachable from the CLI and MCP read
  verbs, not only constructible in the library. A read can weight several
  authors (`fold::TrustBase::PeerContested`), where `Workspace::solo_trust`
  (`src/workspace.rs:123`) is the only trust a surface can select today.
- REQ-4: Multiple signing identities per workspace are supported by an
  **explicit, safe opt-in** that does not trip the `WouldMintSecondIdentity`
  guard (`src/sign.rs`, the #90 fix) — so N role identities appending to one
  workspace is a deliberate choice, never the accidental identity-mint that
  guard exists to stop. A documented `KAN_IDENTITY_FILE`-per-role recipe
  (create keys, wire per-session env, verify attribution) accompanies it (#115).
- REQ-5: `kan show --json`'s ADR-50 contract is pinned and documented — frozen
  field names, additive-only evolution, opaque claims preserved, `SCHEMA_VERSION`
  (`src/json.rs:40`) as the version a consumer checks. The structured `inbound`
  edge (#103) already shipped; this REQ freezes the surface and documents the
  version for the external linter the research loop will build on.
- REQ-6: A read under `PeerContested` over a workspace's role identities shows
  **all** roles' live claims, attributed — the direct fix for the dogfooded
  failure where the director's claim was invisible under `Solo(prover)`. This is
  REQ-3 applied to the multi-role case and is #115's actual acceptance test.

## Acceptance Criteria

- [ ] AC-1: With a published `.claims/` tree in a clone, a `Workspace` read
  surfaces its claims through the wired `Transport` — a test reads a tree the
  local log never wrote and folds it, with no crate-internal linking (#97). (REQ-1)
- [ ] AC-2: `Log::ingest` inserts a foreign-authored `StoredClaim`; `Log::get`
  verifies it against its **own** author (not the local identity), the content
  CID is unchanged, and no re-sign occurs. A same-author record lands in
  `log/repo.car`; a foreign one lands in the overlay and leaves `repo.car`
  byte-unchanged. (REQ-2)
- [ ] AC-3: A CLI/MCP read verb selects `PeerContested` over a named set of
  authors and returns a view weighting them, exercised by a test that gets a
  different result than the `Solo` default. (REQ-3)
- [ ] AC-4: Two role identities append to one workspace through the opt-in
  without the second being refused, and `kan show`/`status` attribute each
  claim to its role. **Negative control:** without the opt-in, the second
  role's first write against a non-empty log is still refused
  (`WouldMintSecondIdentity`) — proving the opt-in, not a weakening of the
  guard, is what enables it. (REQ-4, REQ-6)
- [ ] AC-5: A test pins the `--json` `ShowJson`/`ClaimJson` field set and
  `SCHEMA_VERSION`, failing if a field is renamed or removed (additive-only),
  and asserts an unknown/opaque claim body still serializes rather than
  aborting. (REQ-5)
- [ ] AC-6: In a workspace with prover and director role identities, a
  `PeerContested` read shows **both** roles' live claims attributed, where the
  `Solo` default shows only the active identity's — the exact dogfooded gap,
  now covered. (REQ-6)

## Architecture

Grounded in the seams the design passes already identified and in what
dogfooding showed.

**The reader (REQ-1, REQ-2).** `GitTree::read_all` (`src/transport/git_tree.rs:739`)
already returns byte-complete, signature-verified `(Cid, Claim)` pairs and needs
no change to be the reader; `subscribe` (`:843`) is the same read for the
foreign-author case. What is missing is a caller. `Workspace::open`
(`src/workspace.rs::open`) gains knowledge of a `Transport` and an overlay store
beside `log/`; the index (already disposable, rebuilt on open) rebuilds over the
union of `log/` and the overlay. `Log::ingest` is `append` minus the re-sign
(`src/store/log.rs:689`): it verifies `sign::verify(&author.did, …)`
(`src/store/log.rs:958`) and inserts; the commit stays signed by the local identity,
which correctly attests to the repo's *state*, while each record keeps its own
author's signature. This is `.design/durability-log-recovery.md` REQ-1..4 built.

**The trust surface (REQ-3, REQ-6).** `fold::TrustBase::PeerContested` exists and
is tested (`.design/kan-spine.md` M4a); it has no CLI/MCP selector.
`Workspace::solo_trust` (`src/workspace.rs:123`) is where a surface picks trust
today, always `Solo(my_author)`. The surface gains a way to name several authors
(or "all role identities in this workspace") and fold under `PeerContested`.
This is the machinery that makes another actor's — or another role's — claims
visible, which the dogfooding showed `Solo` hides.

**Multi-role writes (REQ-4), and the tension dogfooding surfaced.** Two
`KAN_IDENTITY_FILE` roles against one workspace mechanically works — two authors'
claims coexist in one `.kan/log`, each keyed by content CID and carrying its own
author signature — *if* both key files are created while the log is empty. The
`WouldMintSecondIdentity` guard fires on the second role's first reference to a
*non-empty* log, because it cannot tell a deliberate second role from the
accidental identity-mint (#90) it was built to stop. The opt-in (REQ-4) is what
gives it that signal: an explicit `--as <role>` or a per-workspace registered
role set marks the second identity as intended, so the guard passes for a
declared role and still refuses an undeclared one (AC-4's negative control).
This is the minimal, plaintext-key-file form #115 itself frames as
acceptable-by-design for *process roles* (not humans) — consistent with ADR-55,
which defers the full derived-key per-agent model (it touches the fold) to a
later milestone and keeps `KAN_IDENTITY_FILE` provisional (ADR-48/49).

**The `--json` contract (REQ-5).** `src/json.rs` is already the versioned
machine surface (`SCHEMA_VERSION`, additive-only, ADR-50); #103 made `inbound`
structured. REQ-5 adds a field-set-pinning test and documents the version, so
the research loop's external linter has a contract to build against rather than
a shape that could drift.

**Relationship to the durability restore and status column.** The reader
(REQ-1/REQ-2) is the durability restore's machinery. Whether the user-facing
`kan restore` command and the `kan status` durability column
(`.design/durability-log-recovery.md` REQ-2/REQ-5) ship *in* v0.8 or as the
immediately-following v0.9 is a sequencing choice (Q1 below), not a design gap —
the primitive they need is REQ-2 either way.

## Resolved Questions

**Does #115 reduce to documentation?** No — proven by dogfooding, not argued.
The `WouldMintSecondIdentity` guard blocks the second role's first write against
a non-empty log, and `Solo` trust hides non-active authors on read. Both the
write opt-in (REQ-4) and the `PeerContested` read surface (REQ-3/REQ-6) are
required. Recorded so a later session does not re-litigate it as a docs task.

**Is per-role identity here the ADR-55 two-layer model?** No. This is the
minimal, interim, plaintext-`KAN_IDENTITY_FILE`-per-role form for *process
roles*, which #115 and ADR-48/49 both frame as acceptable-by-design. ADR-55's
derived-key/enclave per-agent model (which touches the fold) stays a later
milestone; v0.8 does not build it.

### Q1: Do the durability restore command and status column ship in v0.8 or v0.9?

REQ-2 builds the verbatim-insert primitive both the reader and a `kan restore`
need. The user-facing restore command and the `kan status` durability column
(`.design/durability-log-recovery.md` REQ-2/REQ-5) could ship in v0.8 (the
machinery is right there, and the durability pass warned against building the
wiring twice) or as v0.9 (keeping v0.8 scoped to reader + trust + multi-role,
which is already a full milestone). The research loop's stated blocker is
consumption and role attribution (#114/#115), not restore, so restore is not on
the critical path for the loop.

**To resolve** when the v0.8 PR breakdown is committed: include restore+column
as a v0.8 PR if the milestone is not already too large once REQ-1..6 are built,
otherwise open v0.9 for it. Lean: v0.8 ships REQ-1..6; restore+column is v0.9,
built directly on REQ-2's primitive.
<!-- /OPEN -->

<!-- OPEN: Q2 -->
### Q2: One shared `.kan/log` for all roles, or a log per role identity?

Dogfooding showed multiple authors in one shared log works (claims coexist,
keyed by content CID, each self-signed; the commit chain is signed by whichever
identity made each commit). #115's text suggests "each identity keeping its own
append-only log, exactly as if they were separate machines," which is the
per-role-log shape. One shared log is simpler and demonstrably functions
locally; per-role logs match atproto's single-signer-per-repo semantics more
cleanly and pre-stage the sync roadmap.

**To resolve** in the REQ-4 build: confirm one shared log's commit-chain
multi-signing has no correctness problem under the fold (it should not — the
fold reads claim authors, not commit signers), and if clean, ship one shared
log as the simpler form. If any problem surfaces, per-role logs are the
fallback, at the cost of a per-identity log directory.
<!-- /OPEN -->

## Out of Scope

- The full derived-key / enclave per-agent identity (ADR-55's two-layer model) —
  it touches the fold and is its own later milestone; v0.8's multi-role is the
  interim plaintext-key form.
- The personal encrypted backup remote and the publicness ladder (ADR-54) —
  v0.8 reads a *git-tracked* tree, not a network remote.
- Honest cross-republish deletion detection (#92) — needs a new signed
  record-set claim shape; not this milestone.
- `RelationKind` additions (#116) and vector index (#15) — that session marked
  #116 out-of-scope (convention fallback adequate), and #15 stays deferred.
- The day-repo items (day-issue-2/3/4/5 from the same research-loop triage) —
  a different repo, their own PRs.

# Feature: v0.2 — complete the write surface, close the fold's reach

## Summary
v0.1.1-beta.1 shipped a working local-only spine, but two audits this session
(one via a targeted grep, one via a forked full-codebase pass) found that kan's
write surface only ever exercises a small fraction of its own data model:
`ClaimBody::Status`/`Blocker`/`Result`/`Retraction`, every `RelationKind` except
`SameAs`, every `ArtifactRef` variant, `SubjectRef::Anchor`, and a genuinely
usable multi-author story are all fully specified (and in most cases fully
*implemented and tested at the library level*) but never reachable from real
CLI/MCP usage. v0.2's throughline is functional build-out: give agents real
verbs that exercise this machinery. A handful of smaller, unrelated
correctness/completeness findings from the same audits ride along as
secondary fixes, not the milestone's driver.

## Requirements

### Primary: write-surface completion (issue #21 + newly-found Blocker/Retraction gaps)
- REQ-1: `kan resolve <subject> <text>` (existing verb, unchanged signature)
  additionally writes `ClaimBody::Status { value: Resolved }`, `cites`-linked
  to the Resolution claim it's paired with. One agent action, two claims,
  correct provenance — an agent never has to think about "narrative vs.
  structural," resolving something *is* asserting it's resolved.
- REQ-2: new verb `kan block <subject> <text>` writes `ClaimBody::Blocker`
  (currently unreachable) paired the same way with `Status { value: Blocked }`.
- REQ-3: new verb `kan retract <cid>` writes `ClaimBody::Retraction {
  supersedes: cid }`. Looks up the target claim's subject first (so the
  retraction files under the same subject, matching existing test/library
  convention) and checks the target's author matches the caller's own
  `AuthorId` *before* writing — a clear, immediate CLI error ("you can't
  retract another author's claim") instead of letting someone write an
  inert claim that silently does nothing (ADR-16's fold-level enforcement
  stays as the source of truth; this is a friendlier write-time echo of it,
  not a replacement). Works uniformly for "retract a retraction" (ADR-6's
  undo mechanism) — no special-casing needed, `retract` just takes any CID.
- REQ-4: new verb `kan mark <subject> <value>` writes a bare `ClaimBody::Status
  { value }` with no paired narrative — the entry point for `Open`/
  `InProgress`/`Closed`, which have no natural narrative-kind pairing.
  `value` is a `clap::ValueEnum` mirroring `claim::StatusValue`, defined in
  the CLI layer (`src/cli/mod.rs`), not on `claim::StatusValue` itself —
  keeps `claim.rs` free of a `clap` dependency; `actions.rs` maps between
  the two enums at the call boundary.
- REQ-5: `kan same`/`kan resolve` gain `--cites` (matching the existing
  `NarrativeArgs` pattern already used by `observe`/`plan`/`decide`) — no
  justifying reason existed for the omission, unlike every other deliberate
  gap in this codebase, which all carry an explicit doc comment.
- REQ-6: `RelationKind` variants beyond `SameAs` (`Blocks`/`About`/
  `ManifestsAt`/`DependsOn`/`Accepts`/`Rejects`) stay out of v0.2's write
  surface — deliberately deferred, tracked as its own follow-up issue
  (`Rejects`'s exact semantics — does it target a subject broadly, or a
  specific claim via `cites`? — need their own look before committing to a
  verb shape, not something to guess at here).
- REQ-7: MCP tool surface mirrors REQ-1 through REQ-5 exactly (`block`,
  `retract`, `mark` tools; `same`/`resolve` tool params gain `cites`) —
  same "one tool per CLI verb" discipline as ADR-10.

### Primary: git artifact auto-attachment (issue #22)
- REQ-8: every write verb (`observe`/`plan`/`decide`/`resolve`/`block`/
  `retract`/`mark`/`same`) automatically attaches the current `HEAD`
  commit as `ArtifactRef::Commit(sha)` — zero agent effort, matching
  `docs/SPEC.md` §6.2's "anchor to the tightest git object you can" as a
  real default, not just a recommendation nobody follows. New
  `GitSubstrate::head_commit(&self) -> Result<Sha, Error>` (`git rev-parse
  HEAD`) in `src/git.rs`.
- REQ-9: explicit `--file <path>[:<start>-<end>]` flag (opt-in, on top of
  the automatic commit anchor) attaches `ArtifactRef::FileAt`/`LineRangeAt`
  when an agent wants to be more specific than "the whole commit."

### Primary: Anchor-subject enforcement, narrow scope (issue #23)
- REQ-10: `fold::identity::merge_classes` rejects (excludes as a witness,
  the same way an untrusted or cross-author `SameAs` is already excluded)
  any `SameAs` witness where either side is a `SubjectRef::Anchor` —
  `docs/SPEC.md` §5.1's "SameAs between two anchors is a TYPE ERROR, not a
  claim" enforced defensively now, at the library level, even though no
  CLI path can construct an `Anchor` subject yet. Unit-tested directly
  (same pattern `tests/identity_fold.rs` already uses for other
  library-only scenarios) so the follow-up issue that adds Anchor-subject
  CLI syntax inherits a check that's already in place and tested, not
  something it also has to remember to add.
- Anchor-subject CLI syntax itself stays explicitly out of v0.2 (its own
  follow-up, per the earlier decision this session).

### Primary: agent identity — temporary patch, not the real design
- REQ-11: `Workspace::my_author()` (`src/workspace.rs`) reads a `KAN_AGENT`
  environment variable; if set, constructs `AuthorId { agent: Some(derive(
  KAN_AGENT)), .. }` instead of always `agent: None`. `derive` is a
  simple, consistent hash of the agent-name string (e.g. `sha256`) —
  **explicitly documented as a placeholder, not a real keypair**, honest
  about the current trust model rather than implying more security than
  exists (`claim.rs`'s own doc comment calling `AgentKey` "compressed
  public key bytes of the signing agent" stays aspirational until the
  follow-up issue below actually builds that).
- REQ-12: kan's own `.mcp.json` (`#18`) sets `"env": {"KAN_AGENT": "claude-code"}`
  (or similar) on its bundled server entry, so MCP usage gets a sensible
  default agent tag with zero configuration — standard MCP server `env`
  config, no kan-specific protocol needed.
- REQ-13: this closes the *reachability* gap only. Signature verification
  (`sign::verify`) still checks only the human's DID-embedded key —
  unchanged, same trust model as today. File a separate, explicitly-not-v0.2
  issue for the real design (see Out of Scope).

### Primary: identity key encryption at rest (issue #6)
- REQ-14: `Identity::load_or_create` (`src/sign.rs`) tries the OS keychain
  first (`keyring` crate — needs its own lightweight verification spike
  before being trusted, per `CLAUDE.md`'s crate-trust house rule, lighter
  than the MST case but the same discipline), generating and storing a new
  keypair there if none exists.
- REQ-15: falls back to the existing plaintext-file behavior, with a loud,
  explicit warning printed to stderr, when keychain access genuinely isn't
  available (headless CI, a Linux box with no Secret Service daemon
  running) — kan must keep working non-interactively in those
  environments, not hard-fail.
- REQ-16: a migration path for an existing plaintext `.kan/identity` file
  into the keychain (detect it, import it in, leave the file question —
  delete vs. leave as a fallback copy — as an explicit implementation-time
  decision, not guessed at here).

### Primary: MCP resource exposure (issue #28), minimal scope
- REQ-17: one MCP resource — a subject's live claims (the `show` tool's
  data), addressable by URI. Exact `rmcp` resource API shape (attribute
  macro vs. raw handler) needs to be confirmed against the crate source
  during implementation, not guessed at now — same "verify, don't assume"
  discipline the plugin-manifest research (ADR-18) already used successfully
  this session.
- Prompts explicitly out of scope for v0.2 (issue #28 itself calls this
  exploratory; start with the smallest real slice, one resource, before
  investing further).

### Ancillary: witness provenance dropped at the render boundary
- REQ-18: `SubjectView` (`src/fold/mod.rs`) gains a way to carry merge
  provenance — at minimum which witnesses (author, direction, claim CID)
  justified the merge, threaded through from `MergeClass.witnesses`
  (`src/fold/identity.rs`), which already computes this correctly and
  currently has it discarded in `fold::fold`'s `MergeClass` → `SubjectView`
  conversion. `docs/SPEC.md` §4.3 is HARD on this point: "the fold must
  carry its factorization + witness set... NEVER silently promote a long
  weak chain to strict identity."
- REQ-19: `kan show`'s "merged with" line surfaces this — at minimum which
  author(s) asserted which merges, not just the resulting flat subject list.

### Ancillary: give `GitSameFile` a real consumer
- REQ-20: `kan show <subject>` also computes `relations::compute_default`
  (it currently doesn't call this at all — only `status`/`issues` do) and
  surfaces `SameFile`-kind edges as a "related subjects (same file)" line.
  Minimal scope — a read-only surfacing of already-computed data, not a
  new ranking/scoring mechanism.

## Acceptance Criteria
- [ ] AC-1: `kan resolve bug-42 "fixed"` produces two claims: a `Resolution`
      and a `Status{Resolved}` citing it; `kan status bug-42` shows
      `Settled(Resolved)`.
- [ ] AC-2: `kan block bug-42 "waiting on upstream"` produces a `Blocker` +
      `Status{Blocked}` pair, same shape as AC-1.
- [ ] AC-3: `kan retract <cid>` on the caller's own claim excludes it from
      the live set on the next fold; on another author's claim, it's
      rejected at write time with a clear error (not written at all).
- [ ] AC-4: `kan mark bug-42 in-progress` produces a bare `Status{InProgress}`
      claim; `kan status bug-42` reflects it.
- [ ] AC-5: `kan resolve bug-42 "fixed" --cites <prior-cid>` round-trips the
      citation the same way `observe --cites` already does.
- [ ] AC-6: every write verb's resulting claim carries `artifacts:
      [Commit(<current HEAD sha>)]` with no flag needed; `--file` attaches
      `FileAt`/`LineRangeAt` on top when given.
- [ ] AC-7: a `SameAs` witness between two library-constructed
      `SubjectRef::Anchor` values is excluded from merge-class computation
      (unit test, since no CLI path constructs one yet).
- [ ] AC-8: `KAN_AGENT=test-agent kan observe "x"` produces a claim whose
      `AuthorId.agent` is `Some(...)` and differs from an unset-env-var run's
      `None`; two different `KAN_AGENT` values in the same repo produce two
      distinct `AuthorId`s that a `PeerContested` trust base can
      genuinely tell apart (an actual end-to-end proof, not just a library
      test with hand-constructed `AuthorId`s).
- [ ] AC-9: with no OS keychain available (simulated / CI), `kan` still
      works non-interactively, falling back to the plaintext file with a
      visible warning.
- [ ] AC-10: an MCP client can read the new subject-claims resource.
- [ ] AC-11: `kan show` on a merged subject names at least one witness
      (author + direction), not just the flat merged subject list.
- [ ] AC-12: `kan show` on a subject sharing a file-anchor with another
      subject lists it as related.

## Architecture
- `src/cli/mod.rs`: new `Command::Block`/`Retract`/`Mark` variants; `Same`/
  `Resolve` gain `cites: Vec<String>`; new `StatusValueArg` (`clap::ValueEnum`).
- `src/actions.rs`: new `block`/`retract`/`mark` functions; `resolve` extended
  to pair-write; `append`'s shared helper gains automatic artifact
  attachment; a new `PairedAppendResult { narrative: AppendResult, status:
  AppendResult }` for the two-claims-per-action verbs (`confirmation()`
  mirrors `AppendResult`'s, bare CLI stdout stays the narrative claim's CID
  only, matching the existing bare-CID-by-default contract from the AX pass).
- `src/git.rs`: new `head_commit()` method.
- `src/mcp.rs`: new `block`/`retract`/`mark` tools + param structs; `same`/
  `resolve` params gain `cites`; new resource handler (shape TBD per REQ-17).
- `src/sign.rs`: `Identity::load_or_create` gains the keychain-first,
  plaintext-fallback path; new `keyring` dependency.
- `src/fold/identity.rs`: `merge_classes` gains the Anchor-vs-Anchor
  rejection check.
- `src/fold/mod.rs`: `SubjectView` gains witness-provenance data.
- `src/workspace.rs`: `my_author()` reads `KAN_AGENT`.
- `.mcp.json`: gains an `env` entry for `KAN_AGENT`.
- `docs/DECISIONS.md`: new ADR(s) for the write-surface layout, the
  keychain choice (with its verification spike results), and the
  temporary/honest framing of the agent-identity patch.

## Open Questions
None blocking — the two genuinely open items from this session's discussion
(exact write-verb names, agent-identity depth) were resolved in conversation
before this doc was written: `resolve`/`block`/`retract`/`mark` as the verb
layout, and a temporary honest patch (not real per-agent keypairs) for
identity. Implementation-time details explicitly deferred rather than
guessed at: `rmcp`'s exact resource API shape (REQ-17), the plaintext-file
migration's exact delete-vs-keep behavior (REQ-16), and `Rejects`'s precise
target semantics (REQ-6, out of scope for v0.2 entirely).

## Out of Scope
- **Real per-agent cryptographic identity** (separate keypairs, signature
  verification against an agent-embedded pubkey) — REQ-11 through REQ-13
  ship an honest, temporary patch only. Filed as its own follow-up issue,
  explicitly scoped to consider whether this should be a module outside
  kan entirely (agent credentialing is plausibly its own problem domain —
  worth checking for existing solutions, e.g. workload-identity-style
  standards, before designing one from scratch for kan specifically).
- Non-`SameAs` `RelationKind`s (`Blocks`/`About`/`ManifestsAt`/`DependsOn`/
  `Accepts`/`Rejects`) — REQ-6, own follow-up.
- Anchor-subject CLI syntax — REQ-10 ships only the enforcement, not the
  syntax to trigger it from a real command.
- MCP prompts (only resources, and only one resource, ship in v0.2).
- `ClaimBody::Subject`/`SubjectKind` construction — noted during this
  session's discussion as a related-but-separate gap (declaring a subject
  exists with a title+kind), not pulled into v0.2's already-large scope.
- Any of the deliberately-deferred performance work (#25/#26/#27) —
  unrelated to this milestone's theme, no new fixture motivates fixing them
  yet.
